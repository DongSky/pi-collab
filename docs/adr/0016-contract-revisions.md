# ADR-016: Human-confirmed contracts and immutable run inputs

Date: 2026-09-23. Status: implemented for human proposal/confirmation and native execution. Pi coordination tools, semantic compatibility checking and integration gates remain incomplete.

## Proposal, confirmation and publication

A contract has a stable key within a repository and a producing task. Only that task's current Developer owner or a Maintainer can propose revisions or publish them. A proposal records its exact parent revision, definition, format, compatibility claim, migration guidance, optional literal JSON mock and extra affected tasks. Text, JSON Schema JSON and OpenAPI JSON formats are accepted; JSON is syntax-checked, not semantically certified. Breaking changes require a migration guide. The compatibility label is the proposer's assertion until checked by people and later integration tests.

The server expands impact to include the producer, existing bound consumers, explicitly selected tasks and all their downstream tasks. Extra tasks and repository references must belong to the same project. A proposal freezes this affected set. Publication recomputes it; graph expansion requires a new proposal instead of silently omitting newly affected people. Maximum impact is 128 tasks. Published bindings are retained; there is no implicit unsubscribe when someone edits a later proposal's extra list. A task added to the dependency graph after publication inherits the existing contract requirement from its ancestors.

Each affected task's current owner confirms or rejects the exact proposal. A decision is append-only, versioned and idempotent, and records task ownership generation plus project/organization authorization versions. Ownership transfer away and back does not revive an old confirmation; nor does membership removal/regrant or a role change. Latest valid approvals are required. A Maintainer does not impersonate another owner's confirmation: publication can explicitly override missing/rejected/obsolete confirmations with a reason of at least ten characters. The published revision retains both the original decisions and the overridden task list/reason. Owner/Admin MFA applies to sensitive operations.

Publication is serialized with authority, graph and run admission changes using the organization lock, then the contract row. The expected parent rejects concurrent superseding proposals. A lost response can replay the same request; altered payloads cannot reuse an idempotency key. Old proposals and decisions remain readable. Published approval evidence stays frozen even if people later leave. Obsolete proposals cannot be approved or published; owners create a new proposal against the current parent.

The API accepts human session identity only. Definitions, mock data, summaries and decision notes are project data rendered as text; they cannot confer authority. AI-specific proposal tools will use distinct scoped capabilities and will not include approval or override endpoints. This migration does not give Pi browser cookies or database credentials.

## A run consumes fixed contract bytes

Run admission freezes all effective published requirements, including requirements inherited from upstream task dependencies. At most 32 contract versions can be pinned. Existing pins do not change when a new revision publishes, including a queued run that has not started yet. The run may finish isolated work against its accepted inputs; it must explicitly restart to acquire newer inputs for current publication.

The native supervisor writes verified inputs into `../contracts.json`, outside the code checkout and beside the other run-specific data. Each record contains contract ID/key, revision ID/version, the exact canonical body text and its SHA-256. The trusted database generates the canonical text from the immutable proposal. Before Pi starts, the supervisor verifies the hash and content schema. The prompt directs Pi to read the file as project data and to treat mock JSON as sample data. Nothing in the contract body is executed as a platform command. File modes prevent accidental edits; same-user native processes are still not a hostile-code sandbox.

Snapshot capture checks this copy and records the fixed versions. Validation reconstructs the same file in a fresh workspace and checks it after each command alongside source code and dependency copies. Published task results require validation evidence containing exactly the source run's contract pins. Missing/altered evidence cannot promote the result, even when some arbitrary command returned zero. Editing a private copy cannot modify the published revision and prevents ready evidence.

A new contract or revision makes affected runs stale immediately. The recursive dependency validity predicate also invalidates consumers of results whose contract lineage has changed. Unrelated tasks remain valid. A historical validation may remain `passed` for its historical inputs, but cannot publish a current result. Current UI state explains the distinction; old workspaces and historical evidence are preserved. Required-check policy and source/target-specific integration approval are still separate gates to implement.

Contract agreement or mock use does not satisfy a missing real code dependency. A soft dependency permits development with the agreed sample, but an output from that run still cannot publish until a fresh run consumes and verifies real results. JSON mocks are not running servers or installable artifacts. Automatic schema compatibility analysis, API test generation and environment/service mocks remain future work.

## Database and rolling upgrade

Migration `012-contract-revisions.sql` adds scoped contracts, immutable proposals, affected tasks, append-only decisions, revisions, task requirements and run pins. The app can SELECT these records through RLS, and write only through scoped database functions. Composite keys enforce project/task/revision identity. A task ownership-generation trigger protects confirmation provenance; it does not broaden the prior task-owner UPDATE grant. Migrations 001–011 remain unchanged.

New workers use `claim_contract_aware`, `pending_snapshots_with_contracts` and `claim_validation_with_contracts`. Older entry points exclude jobs with pinned contracts, preventing old workers from silently omitting the input file or validation provenance. Jobs with no pins retain their prior eligible paths; contractless snapshot manifests omit the new wire field and new readers default it to an empty list. Historical contractless evidence remains usable only while the task has no effective new contract requirement. Old queued work is never silently repinned during upgrade.

Apply the migration before restarting the updated supervisor. The default backend remains native; contract-bearing Docker jobs are rejected pending parity testing. No runtime restart should interrupt an active writer without checking its state. Backup/retention must retain the contract tables together with referenced snapshots and repository objects; automated retention is not implemented yet.

## UI and evidence

The task panel supports named task selection, immutable definition inspection, owner confirmation/rejection, explicit Maintainer override, stale proposals and pinned run inputs. A draft retains its selected parent even when background data refreshes; it cannot silently propose old text against a newly published version. Failed network responses preserve the same operation for retry. Current contract publication events refresh active run panels; other views have visible-page polling and visibility-resume fallback. Dedicated notification delivery and latency/load acceptance remain pending.

Seven real PostgreSQL/Pi/native-command tests in `tests/collab/contracts.test.ts` cover impact closure, identity boundaries, immutable grants, concurrent replay/publication, stale decisions after ownership/authority change, Maintainer/MFA override, graph changes, conflicting parents, live Pi input retention, direct and recursive invalidation, missing soft input, legacy-worker exclusion, corrupted content and forged/omitted validation provenance. No real external model inference is used.

The isolated browser suite has two owners confirm a contract, tests authorization and Origin rejection, loses/retries proposal and publication responses, runs a real Pi diagnostic against the fixed mock, validates its snapshot, publishes a result, publishes a breaking revision with an explicit override and observes old evidence rejection. Desktop and 390px layouts are checked. Screenshots are `test-results/collab/contracts*.png`.

Repeated browser acceptance also exposed an existing initialization race: a late Strict Mode configuration response could replace a repository already selected by the user. Configuration effects now have local cancellation and preserve valid selections. The test deliberately delays the earlier response until after selection, then checks both the selector and the admitted workspace repository. This corrects the earlier intermittent scope-warning timeout; the warning correctly excluded a peer in a different repository.
