# ADR-044: Durable read-only PR proposals from acknowledged pushes

Status: implemented for the native Git service, HTTP endpoints and browser. Migration 030 adds read-only preparation; explicit creation and head reservations are implemented separately in ADR-045. Full revisions, CI and protected merging remain required. A ready proposal is not permission to send.

Subsequent implementation: [ADR-045](0045-durable-draft-creation.md) adds a separate explicit creation action, shared head reservations and initial ChangeRequest observations. Read-only preparation retains the behavior below; full revisions, CI and protected merging remain pending.

## Source and current authority

A proposal starts from an actual, positively acknowledged durable task-branch delivery. Queued, rejected, not-sent, unknown and retired deliveries cannot qualify, even when a later observation finds the same SHA at the remote. The source is the acknowledged immutable export, task/workspace identity, manifest hash and repository binding. Preparing a proposal neither rereads a mutable source checkout nor pushes the commit again. The remote default branch may have advanced; the read-only provider protocol observes a fresh base for the same delivered head.

Admission checks the current task Developer owner or project Maintainer, organization/project membership and any organization MFA requirement. It records both authorization versions and the exact current task version. The earlier push's human grants have already been spent; historical attribution is retained, but new proposal authority belongs to its current requestor. Source installation and repository binding versions must still match the acknowledged delivery. Credential rotation/rebinding that changes those versions requires a separate verified upgrade path; this increment does not silently reinterpret the old source.

The user submits title, body and expected task version, never source IDs, a refspec, GitHub URL, observed SHA or credentials. SQL derives the entire source. Idempotency is scoped to delivery + actor + request key and compares the exact normalized payload before new credential work. A terminal retry returns the original record; the same key cannot change its text or restart a failed/cancelled read. New requests use new IDs. At most one queued/running reader exists per delivery and 20 per project.

## One read, one durable publication

The existing restricted Git service adds a sixth processor while retaining two shared lanes. A session advisory lock, backend PID and unguessable claim nonce pin one job to one SQL connection. The worker checks admission again before opening the encrypted App key and requests only single-repository `contents: read` and `pull_requests: read` credentials. It never calls the provider create method. A live monitor checks current authority every 500 ms; a silent SQL response is bounded locally at two seconds and discards that connection. Revocation/cancellation aborts the provider read while independently attempting token cleanup.

After a completed read and confirmed credential cleanup, the worker creates the exact draft request described in ADR-043. The proposal ID is its future operation ID. The request fixes the human title/body, generated head/default base, delivered head, freshly observed base and provenance footer. SQL independently derives and compares the intent and the complete generated request, and computes the SHA-256/UTF-8 byte length from the exact serialized request text. It separately validates provider scope, installation, head/base, observation freshness, existing-PR identities and confirmed cleanup before publication. Original observation text is stored alongside JSONB and its hash; JSONB's reordered keys are not used to reconstruct the evidence bytes.

Final publication holds the current user, task, binding and installation rows under the existing authorization serialization protocol. A changed member grant, task version, binding or installation cannot become ready using an earlier read. After publication these changes make `valid` false without rewriting historical evidence. `valid` refers only to current local authority and source binding; it does not claim that a sampled remote branch remains unchanged.

Jobs progress from queued to running to ready, existing, failed or cancelled. An existing PR is an observation, never adopted as this operation or treated as a successfully created ChangeRequest. A vanished SQL owner makes an unfinished read fail on recovery; it cannot be reassigned to repeat the provider request. If publication actually commits but its COMMIT reply is lost, the broker does not reconnect or overwrite the outcome. The original idempotent request and context read recover the ready record without another token.

## Browser and HTTP boundary

After an acknowledged delivery, its card exposes **准备草稿 PR 提案**. Authorized users enter a title and description; project readers can inspect the same immutable result. The UI explicitly states that preparation does not create a PR or notify repository members. It shows the delivered SHA, sampled target and timestamp, complete generated title/body, exact serialized request and evidence hashes. Provider links come only from checked repository identity and PR numbers; title/body are rendered as literal text.

The browser stores its pending request number and complete payload before submitting. Reloads retry that same request. A source binding becoming invalid does not prevent a still-authorized member from reconciling an already-admitted request; a never-admitted request still fails admission. Cancellation uses a separate durable key and reason, and only applies to queued/running reads. Polling pauses while hidden, resumes on visibility/network recovery and ignores out-of-order responses. Each context response includes the latest 20 proposals; complete historical pagination belongs to the subsequent history/retention work.

Endpoints are `push-deliveries/:id/pull-proposals` (GET/POST) and `pull-proposals/:id/cancel` (POST). They require current identity/project authorization, same-origin mutations and no-store successful reads. The Web role has only the public wrapper functions; the Git role has narrowly granted claim/begin/live/finish/fail functions and no direct proposal or credential-table access.

## Required next boundary

Read-only proposals do not reserve the remote head or stop other platform pushes. Their observations are bounded samples. Actual creation must explicitly confirm the complete saved request and its notification effect, acquire the global GitHub repository-ID/head-ref fence shared with push confirmations, revalidate current local/remote authority, and receive a positive final SQL COMMIT before exactly one provider POST. Unknown creates must retain that fence; markers, current absence or revoked credentials cannot settle them. Known created PRs need a ChangeRequest association and immutable revision observations. None of those effects are enabled by migration 030 or by a proposal becoming ready.

## Verification and deployment

Native tests use real PostgreSQL, actual Pi tool-created commits, authenticated Git HTTP delivery and a loopback PR REST fixture with generated App credentials. They cover concurrent admission/claiming, raw-byte evidence, newer baselines, ordinary later source edits, current roles/MFA, unknown delivery refusal, cancellation, grant/version changes, forged evidence, restricted SQL, owner loss, real dropped COMMIT replies, held authority rows and silent SQL/provider reads. Browser acceptance covers two members, actual lost POST response and reload retry, generated literal content, hashes, cancellation, existing PR observations, revocation and desktop/390px layouts. These are protocol fixtures, not real external GitHub acceptance or model inference.

Apply migration 030 before starting or gracefully restarting the single Git service to load the sixth processor; do not start a duplicate instance. Migration 030 is now applied to the main local database and its stored hash matches the source. Migrations 001–030 are immutable; later schema fixes require a new migration. No Docker dependency, `next build`, personal credential import or automatic remote PR creation is introduced. Final evidence is recorded in the implementation status.
