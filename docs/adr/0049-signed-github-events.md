# ADR-049：签名 GitHub 事件与旧证据失效

- 状态：已实现并通过相关数据库及双浏览器验收；迁移 035 已应用本机主实例，源码摘要已核对，从此不可修改。
- 前置：[ADR-046](0046-durable-pull-observations.md)、[ADR-047](0047-fixed-pull-revisions.md)、[ADR-048](0048-fixed-revision-ci.md)。

## 接收与密钥边界

新增 `POST /api/collab/github-webhooks/:appId`。它不以浏览器登录授权；带 Cookie、Authorization、Origin 或浏览器 Fetch Metadata 的请求被拒绝。继续使用既有 Host 校验，没有放开其他 API 的来源检查。HTTP 层限制四项并发、2 MiB 原始请求和十秒读入期限；收到明确 SQL 提交结果才返回 202，数据库不可用或回应未知返回可重试 503。

本机操作员用 `github:webhook` 命令为已登记安装配置专用验证密钥。数据库同时要求对应组织 Owner/Admin 和 MFA、准确配置版本及幂等请求编号。命令只读显式指定的 0600 普通文件，拒绝符号链接、硬链接、超长内容和换行，不打印密钥。同一 GitHub App 的不同安装需配置其共同的 App webhook secret；每个组织的配置授权独立。轮换与停用立即增加配置版本并使关联 PR 的旧证据失效，不接受旧密钥过渡窗口。

专用 HMAC 验证密钥保存在数据库的私有 `collab_git.webhook_keys` 中，由 `SECURITY DEFINER` 函数使用现有 pgcrypto 校验。Web 和 Git 运行角色均不能查询密钥表，浏览器、Agent 和接口返回中没有密钥；没有借此向 Web 提供 GitHub App 私钥或访问令牌。该验证密钥属于数据库备份的敏感内容，应随数据库执行既定的访问和加密备份要求。它只用于验签，没有远端读写能力。

## 字节、归属与重放

SQL 对收到的原始字节计算 HMAC-SHA256，用固定 32 字节、无提前退出的比较核对 `X-Hub-Signature-256`。再验证 URL App ID、有效的已登记 installation ID、仓库 owner ID 和当前本地仓库关联；不能通过正文中的 sender 或 URL 认领未知 PR。支持 App ping，以及 `push`、`pull_request`、`check_run`、`check_suite`；其他事件不作为已处理接受。

`X-GitHub-Delivery` 和事件类型 Header 不在 GitHub 签名字节内，因此不能仅按投递编号去重。每个安装同时保存首次接收的 delivery ID 与原始字节 SHA-256；重复编号必须对应相同内容和事件，重复内容即使换了编号也不再次生效。重复内容不新增别名行，防止拿同一份已签名字节无限填充投递表。正文结构必须与事件类型相符；原始正文不落库，只保存摘要、字节数、事件种类及限定的身份/SHA 字段，不保留 PR 正文或检查注释。

首次接收记录和所有受影响 PR 的失效计数在同一事务提交。数据库事务锁与观察/代码/CI 发布使用同一组织授权锁，因此通知和证据提交有明确先后关系。返回丢失后的重投只读取持久结果。签名证明来源，通知本身永远不提供检查通过或合并授权。

## 代码与 CI 的独立失效

- `pull_request` 只影响已经归属该仓库和 PR ID 的 ChangeRequest。
- `push` 只影响该 PR 最近观察中的源分支或目标分支；其他分支和标签不触发失效。
- `check_run` / `check_suite` 只影响最近有效观察中的准确 head SHA；旧历史代码版本上的事件不影响新版本 CI。

代码事件递增代码与 CI 两个计数。观察作业在准入时固定代码计数；读取过程中有通知，最终发布被拒绝。固定代码来源只接受计数仍一致的最新成功观察，所以既有下载或下载中的作业不能被误作当前代码。成员仍能查看原历史差异，再显式读取状态、获取新版本及 CI。

检查事件只递增 CI 计数，不迫使用户重新下载未改变的代码。CI 作业准入固定该计数，运行中变化或旧成功都不能通过当前资格判断；新的显式读取仍须通过准确 SHA/生产者/状态与 TTL 校验。

计数只增长，不用通知中的状态、事件发送时间或结论覆盖持久观察。延迟到达的通知可以再次要求刷新，但不能使状态倒退或恢复旧绿灯。页面每三秒读取本地通知/证据，不自动访问 GitHub、执行代码、发送评论或合并。

## 使用与后续

安装管理展示配置版本和最近有效通知时间。项目成员在 PR 状态面板看到配置状态、需要重新读取的提示及最近二十条已验证通知，读接口检查当前项目权限。没有收到通知不代表远端没变化；轮换期间投递失败可从 GitHub 重投。

验收包括原始字节篡改、错误签名、安装/仓库隔离、浏览器凭据拒绝、并发重复、换 delivery ID 重放、代码/检查分离、旧 SHA、无关分支、读取中变化、密钥轮换/停用、大小限制及共享界面。双浏览器通过真实本机 HTTP 向独立测试站点投递签名事件，远端 Provider 仍是生成凭据的回环 fixture，没有替用户更改外部 GitHub App 配置。

最终相关观察/代码/CI 回归 33/33、独立提交故障测试 2/2、安装权限/旧入口门禁 9/9 通过，类型检查和全量 lint 通过。主实例升级保留原仓库、两个已完成真实模型运行和成功 Git 推进，未生成 webhook 密钥或投递。

安装卸载/权限变化的生命周期、远端按版本人工评审、受保护合并、自动刷新策略、投递保留/运维告警和真实外部账户验收继续属于整体计划，不以此增量代替完整 Git 交付。
