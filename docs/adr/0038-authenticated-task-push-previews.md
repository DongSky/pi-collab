# ADR-038: Read-only remote capture for task push previews

Status: accepted for the internal native preparation path; durable admission, history UI and dispatch integration remain outstanding.

## Context

ADR-036 requires an authenticated remote baseline. A local repository HEAD, a prior import's SHA or a user-supplied observation hash cannot prove which objects the remote currently owns. The default branch may have advanced since a task began, and those new objects need not be present in either the task checkout or the platform's shared local repository. Preview generation must acquire current remote evidence without changing either of those sources or acquiring write credentials.

## Decision

`createTaskPushPreview` accepts server-bound preview/export and operation IDs, task/source identity, exact source revision/HEAD and the repository binding. Its schema accepts no remote baseline SHA, expected-old ref, arbitrary URL or observation hash. Current platform membership, source exclusivity and binding authorization remain the future durable broker's responsibility.

The helper first verifies the stopped native workspace and exact local revision/HEAD. `GitHubReadClient.readTaskPushTarget` then verifies the installation's ability to support a future write, but requests a token with **only `contents: read` for one repository**, plus implicit metadata read. The existing read-client expiry, response bounds, cleanup and scope checks still apply. A read-only installation cannot enter this push preparation path; ordinary repository inspection/import continues to support read-only installations.

Read-only preview and write preflight share `github-task-target.ts` for stable repository identity, explicit privacy/visibility, default/integration destinations, exact task ref and active branch rules. The same task/workspace namespace is generated by the server. Both absent and existing task branches are checked. Existing refs must point directly to commits and agree with the branch response. Any active branch rule or protection refuses this path; there is no App bypass.

The client's read capability only exposes upload-pack for its fixed repository. It downloads the complete observed default-branch history into a fresh `task-push-captures/<export UUID>/git` bare repository, with no remotes or credential helpers. It never fetches into the task or shared repository, advances their branches, or acquires a receive-pack capability. The downloaded SHA and Git object integrity are checked using the existing managed Git import path.

After the transfer, the client repeats installation, repository, ref and rules observations. The default SHA and task ref must equal their pre-transfer observations. A rename, privacy change, suspended installation, protection/rules change or inconsistent evidence refuses the result. Successful token revocation is required before returning read evidence. A changed workspace is rejected by the exporter's repeated revision/exit checks. These observations are not atomic with future repository administration; the separate write client must still recheck at dispatch.

The returned baseline read evidence and final task-target evidence form one observation document with a SHA-256. The exporter derives its remote SHA and expected-old commit from that document. It uses the private capture as its known baseline store, then performs ADR-036's complete new-history checks and creates the immutable export. The manifest pins `captureId` to the same export UUID and retains the authenticated observation hash. Legacy internal exports without a capture ID continue to use their broker-owned repository; neither storage selector grants authority.

The new export preserves the task's original SHA and does not merge in the newer remote default branch. Such integration remains an explicit separate operation. The current task ref must be an ancestor of the task HEAD for an update; an unrelated/replaced remote task branch is not repaired or force-pushed. All new commits relative to the known default history are checked, including previously pushed task history. An already-identical task ref produces no new push preparation.

## Immutable export versus temporary capture

The completed export is self-contained. Its later verification uses the authoritative manifest hash and its own objects/base pack, not the capture directory or mutable workspace. Removing a temporary read capture does not alter an already verified export. This property is tested; it is not an instruction to manually delete deployment data before retention policy exists.

A partial read, failed revocation, inconsistent provider observation or rejected history does not produce a usable completed export. Failed capture/export directories may remain and their IDs are never overwritten or resumed by this helper. Source objects, index, drafts and shared repository contents remain unchanged. The future durable queue must deduplicate **before** reading credentials, track these orphan resources, and verify current authority before publishing a preview. A local file, returned hash or successful read alone cannot authorize a push.

## Planned durable lifecycle

New database work begins at migration 027 or later; applied migrations 001–026 are immutable. The next integration must establish:

1. A scoped, idempotent preview request with current member/MFA/task/run/binding/installation versions and exact source revision/HEAD. Workspace Git writers and snapshot capture must be excluded while the preview reads source history.
2. A broker claim using the dedicated Git role and a pinned SQL connection. Provider reads happen outside long permission-lock transactions. Only the current claim and still-valid authorization may persist the observation, manifest hash and reviewable outgoing commit set.
3. Explicit confirmation of this immutable export, destination identity/visibility, default and expected-old SHA, and the complete outgoing history. Confirmed dispatch owns one generated remote destination until its effect is safely settled. Changed policy-relevant evidence requires a fresh preview/confirmation.
4. Current final authorization and a durable exact-byte dispatch record before requesting the remote effect. Unknown receive or SQL acknowledgement results retain occupancy and must not be replayed. Credential cleanup and Git effects remain separate, as in ADR-037.

The preparation helper has no HTTP route, service queue handler, database grants or browser confirmation. It is not a substitute for any of these lifecycle requirements.

## Evidence and deployment

`tests/collab/task-push-preview.test.ts` uses generated App keys and scoped read tokens, real loopback REST/upload-pack, actual native Pi tool commits, and a separate write client against a real Git receiver. It verifies exact SHA preservation, retained drafts, no write token during preview, a newer remote absent from both local repositories, an existing task ref independent of the default baseline, stale source/scope refusal, changes during upload, cancellation/cleanup failure, intermediate secrets, immutable replay and capture removal.

This path uses native Node/Git/Pi and requires no Docker. No personal credentials, external model inference or real GitHub account is used for these tests. External-account acceptance, database/browser concurrency and optional Docker parity remain separate work.
