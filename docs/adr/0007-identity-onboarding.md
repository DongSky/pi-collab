# ADR-007: Transactional onboarding with Better Auth

Date: 2026-09-23. Status: implemented and locally verified for the account flows below; full M1 authorization/executor work is ongoing.

Better Auth 1.7.5 owns password hashing (scrypt), password verification, cookies, sessions, TOTP, encrypted recovery codes, reset token issuance and consumption. Public sign-up remains disabled. We use its maintained crypto function to prepare credentials, then narrow PostgreSQL security-definer functions atomically insert the pinned auth schema and organization/project membership. This coupling is intentional: an invitation must not be consumed without the account and membership, and failed provisioning must not leave an orphaned account. Integration tests log into accounts produced by these functions. Auth upgrades require migration and compatibility tests before deployment.

Bootstrap requires a locally generated 256-bit token, stored hashed in the database. A transaction lock permits exactly one initializer. Initialization closes permanently once consumed; development seeds also consume initialization. Invitation tokens are random, hashed at rest, single-use, bound to normalized email, and expire after 48 hours. Invitation URLs carry their token in the fragment, which is submitted in a POST body rather than an access-log URL. Existing accounts must sign in as the matching user; an invitation cannot change their password, reactivate disabled memberships or change existing roles. Acceptance rechecks the inviter's current role, sharing an organization transaction lock with membership changes.

Owner/Admin invitations and organization membership changes require enrolled MFA. Administrator MFA cannot be disabled. Successful initial enrollment revokes sessions issued before MFA was enabled, and the auth library issues a fresh session after verification. Role/deactivation changes revoke the affected user's sessions immediately. The last active organization Owner cannot be removed, including concurrent self-demotions. Project-management and future run/broker authorization must continue to use current database state; session deletion alone does not stop an already executing agent. Executor revocation remains outstanding.

Login throttling deliberately ignores forwarded-IP headers until a trusted ingress contract exists. The maintained limiter uses shared per-path buckets; this is conservative and can affect teammates sharing a login endpoint. Public bootstrap/invitation limits are persisted outside failed provisioning transactions. Sensitive API errors are mapped from an explicit allow-list rather than returning raw SQL errors.

Local password reset delivery uses private 0600 files under the development data directory. Production requires explicit SMTP configuration (`PI_COLLAB_MAIL_TRANSPORT=smtp`, `SMTP_URL`, `SMTP_FROM`); file mailboxes are rejected in production. No external emails were sent during implementation. Native and Docker business code use the same transport selection. Invitations are explicitly shared links; creating an invitation does not silently send email.

`npm run test:collab:identity:e2e` copies only application source/configuration into a temporary private directory and uses a disposable database. Its Next process owns its own `.next` and generated files. Multiple Chromium contexts cover first-install UI, MFA, invitation registration/replay, password reset, session revocation and last-Owner protection. Neither the active checkout nor development accounts are reset. Server logs remain local and private; CI uploads only screenshots after secrets have been hidden.

Remaining work includes project member lifecycle/recovery, administrator recovery when every factor is lost, sensitive-operation step-up policy, SMTP deployment verification, account security audit presentation, executor/token revocation and the remaining M1-M4/P2 plan. This ADR is not a claim that those milestones are complete.
