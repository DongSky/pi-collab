# ADR-018: Managed PostgreSQL resources, fenced leases and broker jobs

Status: native implementation accepted for the documented scope; broader resource lifecycle and deployment acceptance remain open. PostgreSQL is the first concrete adapter; port isolation, other external services and Docker parity remain separate work.

## Authority and isolation

A project Maintainer with the existing MFA requirements creates a named PostgreSQL test resource. The separate resource broker provisions a random `pcr_<uuid>` login role and schema in the local PostgreSQL instance. The role has no superuser, role/database creation, bypass-RLS or server-file privileges, and no grants to platform data or sibling resource schemas. Project members see resource IDs, names, occupancy and authorized job results, not connection credentials. Resource passwords use AES-GCM with project/resource/version AAD and a separate private master key. The app and executor roles cannot read the vault. A missing key is only initialized when the database contains no encrypted resource credentials; existing data with a lost key fails closed.

Pi receives resource tools through the existing run-scoped coordinator. SQL credentials stay in the broker process and its dedicated SQL connection. Ordinary shell tools receive neither broker database credentials nor shared resource passwords. This is a trusted local development arrangement, not adversarial same-user host isolation: all native processes still share host privileges, PostgreSQL CPU/storage capacity and catalogs. SQL roles block cross-resource/platform data access through the supported path, but this is not a hostile multitenant database service. Control-plane/data-plane separation into independent database instances, host/network isolation and PostgreSQL resource quotas need further deployment work.

## Atomic acquisition and monotonic generations

`collab_request_resource` requests one to eight same-project resources as one batch. There is at most one active batch per run; a run cannot hold one batch while waiting for an additional one. IDs are sorted and deduplicated. Waiting requests hold no resources. An earlier waiting batch takes precedence over later overlapping requests; unrelated available batches may proceed. The initial waiting timeout is five minutes.

Each successful assignment increments the resource's database-owned epoch and freezes that fence in its grant record. The resource lease lasts 30 seconds. The executor renews it after successfully renewing the run lease; an already expired resource lease cannot be revived. Every resource call checks current run/executor/epoch, organization/project authority, status and lease. Each new SQL job also requires the exact request/resource/fence tuple. Old holders cannot submit new writes when a later owner takes over. Replayed request UUIDs preserve the original result; altered payloads fail.

`collab_release_resource` cancels waiting batches or transitions a held batch to releasing. Stop, revocation or lease expiry have the same releasing effect. Pending SQL jobs are cancelled; running jobs receive a stop request. The batch remains unavailable until all old database writers are confirmed gone. Fixed initial bounds are 16 resources/project, 100 SQL jobs/run, the coordinator's existing 200 successful mutations/run, four broker jobs/process and one unfinished job/resource. These are not configurable scheduling policy yet.

## SQL execution and uncertainty

`collab_execute_resource` queues an immutable SQL string, hash, source run, resource and fence. The broker uses the resource's own role and schema. It begins an explicit transaction, registers the real backend PID/start timestamp/role against a unique dispatch ID, then executes one named prepared statement. Extended protocol forbids multiple statements in a single submission. Top-level transaction/session/copy commands are rejected; statements with leading whitespace and nested comments are parsed conservatively. Procedures or anonymous blocks cannot commit out of the explicit transaction. Role grants, not keyword filtering, protect platform/sibling data.

Jobs have a 20-second SQL timeout, five-second lock timeout and 25-second broker watchdog. Result collection is bounded to 100 rows/64 KiB; exceeding it cancels the transaction. Exact bounded evidence records command, row count, rows, SQL hash and acknowledged commit. Completion requires the registered backend to be absent before marking it stopped; success also requires the expected evidence fields/hash and a registered backend. SQL success does not certify a repository snapshot, dependency combination or integration candidate.

The broker checks authorization/grant validity while a job runs and before COMMIT. Cancellation terminates the exact registered PostgreSQL backend, identified by PID, start timestamp, database and resource role. No arbitrary PID or user-supplied operating-system signal is accepted. A commit may still race with loss of its acknowledgement: once COMMIT has been attempted, failure to observe the reply is `unknown`, even if the data really committed. It is never automatically rerun. A later read may inspect data, but the previous job's outcome remains historical evidence.

Broker job heartbeats expire after 15 seconds. Reconciliation invalidates the old dispatch before inspecting the session. An unbound late starter can no longer register or launch SQL. A registered surviving backend is terminated; only positive absence permits releasing the resource. Unknown outcome and stopped writer are distinct fields: the platform can confirm a writer exited without claiming its SQL did or did not commit. The current proof assumes the configured single local PostgreSQL instance; cross-host failover/split-brain and disaster recovery require separate acceptance.

## UI, compatibility and operations

The project resource panel is reachable from task views. It supports Maintainer creation, lost-response retry, occupancy, waiting batches, lease generations, recent SQL evidence and unknown/stopping explanations. It uses project events plus visible-page/resume polling. It shows at most 100 active requests and 50 recent jobs. Pi reads current grants and recent job summaries with `collab_get_context`; large result previews are truncated explicitly, with full authorized results in the project UI. Human operators can stop the run from its existing control panel. Migration 015 adds resource-only administration and cancellation, described below.

Migration 014 creates the resource tables and restricted `pi_collab_broker` function surface. Existing migrations 001–013 are unchanged. Apply 014 before restarting the updated executor/web/broker. `dev:local` now manages the broker as a sibling process and stops the group if any service exits. Old runs without resource tools do not acquire these grants. Docker does not receive the native coordination endpoint, and no Docker support is implied here.

Resource schemas/roles, the credential vault, request/job history and the resource master key must be backed up together. Disposable test databases remove only their own recorded resource roles after dropping their database. Automatic production retention, destructive resource reset/delete, per-workspace automatic database allocation, isolated port namespaces and non-PostgreSQL adapters are not implemented. PostgreSQL resource SQL can intentionally damage its own schema; operators should treat it as disposable test data.

## Evidence

`tests/collab/resources.test.ts` uses real PostgreSQL connections and native Pi processes. Its 12 tests cover nonblocking claim contention, role/data boundaries, real DDL/DML persistence, reversed concurrent batches with no partial holdings, wait timeout/cancellation, increasing fences, stale/cross-project denial, exact live-writer rejection, crash before backend binding, actual network disconnection, process-level SQL termination and rollback. One TCP proxy lets an actual INSERT commit and then drops its actual COMMIT reply; the persisted job correctly remains unknown. Two Pi processes overlap while requesting the same resource and preserve independent code files. A local Responses protocol fixture drives real Pi through resource acquisition, SQL submission, cancellation and release; no external inference is involved.

The browser fixture verifies creation permissions/Origin/lost-response retry, two-user occupancy and waiting, real PostgreSQL job evidence, grant progression, release, reload and desktop/390px layout. Its run-control steps are explicitly simulated; the separate native/protocol tests verify real Pi behavior. Screenshots are `test-results/collab/resources*.png`.


## Human resource administration (migration 015)

Maintainers can disable and re-enable resources with a recorded reason, optimistic resource version and idempotency key. The existing organization role/MFA policy applies. Authorization is checked before replay; a revoked member cannot reuse an old successful command. Disabling increments the fence immediately, cancels entire waiting batches that contain the resource and drains active holders using the existing writer-exit protocol. SQL jobs may become unknown while draining; administration never changes that evidence to success or a retryable failure.

Enabling requires no holder and no unfinished writer. It preserves the same schema/data/credentials, creates no new writer and never revives cancelled batches. A resource disabled before provisioning returns to requested on enable. No delete, reset, force-release or direct credential export is provided.

Developers can cancel their own submitted SQL jobs and release their own resource requests; project Maintainers can do this for any project run. Reviewers and unrelated developers cannot. These operations record a reason and append a command/audit/event under the organization serialization lock. Queued jobs cancel immediately; running/unknown jobs must still exit before the lease can move. Cancelling a job leaves its batch held; releasing a batch does not stop the AI, which may request it again. Disabling the resource is the operation that blocks new requests.

The browser shows actions only for the applicable authority, captures reasons, preserves the original payload when a response is lost, and displays draining separately from disabled/available. Six additional database tests cover concurrent replays, stale versions, scoped/read-only authority, preserved schema/data, pre-provisioning disable, real live writer drain, human cancellation/release, unknown writer reconciliation and revoked replay. Browser acceptance covers permissions/Origin, actual user actions, lost disable response, stale enable version, literal rendering of reasons, shared observations and desktop/390px layout. Reset/delete, configurable quotas, automatic allocation and Docker parity remain open.
