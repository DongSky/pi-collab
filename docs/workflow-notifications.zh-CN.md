# 协作流程通知与静默时间

迁移 064 补齐原计划 6.3 中分散的工作流通知。页面入口是顶部「收件箱」；点击通知打开对应项目和任务，讨论通知继续定位到话题。通知与业务状态在同一数据库事务内保存，不使用浏览器在线状态决定是否投递。

## 接收范围

- 控制权申请通知当前控制者；同意、拒绝或失效通知申请者，撤回通知控制者。任务订阅者也可收到变化。重复提交原请求不重复通知。
- 任务进入评审、组合验证通过、GitHub PR 或 GitLab MR 转为待评审时，项目中当前有效的 Reviewer/Maintainer 可收到通知，无需先发现并订阅任务。跳过发起该动作的人和任务作者的角色广播；主动取消该任务订阅后不再接收角色广播。直接参与的控制交接仍通知当事人。
- GitHub 必需检查的已完成非成功结果产生检查未通过通知；缺失、等待或来源不匹配不伪装成 CI 执行失败。读取失败使用单独提示。相同固定版本、策略和检查 ID 的重复读取只通知一次。
- 组合冲突、检查失败或未知结果通知任务负责人、订阅者和整合发起人。本地受评审 Git 推进成功后，来源任务及同仓库仍在进行的相关任务收到基线更新通知；原工作区不改写，通知不自动变成 AI 指令。
- GitLab 已确认的待评审、合并、失败和未知状态进入收件箱；读取到与固定提交一致的失败流水线时按流水线 ID 去重。
- 运行完成、失败、取消、待核查，以及业务状态实际进入 waiting_input 时，通知发起人与当前控制者。AI 和人工终端共用运行通知。迁移 067 已接通 `collab_ask_user` 的实际等待问答流程，见 [AI 提问与回答](run-questions.zh-CN.md)。

普通事件继续按任务订阅投递，负责人在未主动取消时默认订阅。所有接收者在投递时必须仍属于该组织和项目；读取、未读计数与标记已读均按当前成员权限和本人身份过滤。通知不能授予控制权或评审资格。

GitHub/GitLab 通知来自已完成的显式读取和交付结果；没有新增外部轮询或外部消息发送。邀请仍通过既有邀请链接和配置邮件通道处理；没有把未知邮箱虚构成已存在的收件箱账户。

## 个人静默

在收件箱选择 1、8 或 24 小时，点击「开始静默」。设置保存在服务端，刷新及其他已登录设备沿用同一结束时间。静默期间顶部隐藏未读数量，展开收件箱仍显示通知及未读数；新通知继续保存，不自动标记已读。

点击「恢复未读提示」可提前结束；到期后下一次状态刷新自动恢复，前台最多约 10 秒。设置更新有版本检查，其他窗口已修改时刷新核对，不静默覆盖。API 仅允许修改自己的设置，结束时间必须在未来 30 天内；账户 A 的设置不影响账户 B。

当前是一次性静默时段，按周循环的免打扰日程、分类偏好、邮件摘要和保留期限另行保留。静默不会停止 AI、跳过权限检查或清除审计。

## 验证方式

- `tests/collab/run-control.test.ts`：实际控制交接通知、幂等、静默期间投递、到期、并发设置冲突、个人 RLS、评审角色广播、取消订阅和撤权。
- GitHub 检查/交付专项：真实本机协议读取必需检查，验证待处理不报失败、失败通知与重复读取去重；受保护交付流程继续通过。
- GitLab 专项：真实 Git/本机 API 产生待评审、失败流水线及合并通知。
- 本地推进专项：实际 Git 写入后失联，核查成功才产生基线通知，重复完成不重复投递。
- 双成员浏览器：静默、刷新、账户隔离、CSRF、收件箱申请定位、恢复未读、交接决定定位、后续指令及停止；桌面/390px 页面。

本机协议服务验证不等于真实外部 GitHub/GitLab 账户验收。
