# 将成员讨论选入当前 AI 上下文

迁移 065 补齐开发计划 6.2 的显式讨论交接。普通讨论、提及和新回复仍只属于成员协作；只有当前 AI 控制者确认发送时才产生运行指令。

## 使用流程

1. 在任务中选择一个正在运行的 AI，打开「讨论与代码建议」中的话题。
2. 当前控制者展开「选取讨论交给当前 AI」，选择 1–20 条已加载评论。长讨论可以先加载更多回复。
3. 填写交接说明，选择「当前工作后继续」或「调整当前方向」，点击「预览所选讨论」。预览显示固定的话题、作者、评论内容和已有代码锚点。
4. 核对后点击「确认发送给当前 AI」。预览本身不会发送；未选评论和后续新回复不会加入。
5. 「成员指令记录」显示实际发送者、原讨论标题、评论数量和来源 hash。点击来源返回话题；完整发送文本保留当时作者及内容，原讨论后续解决或新增回复不会改写历史。

交接只把选中的文字及来源引用交给当前运行，不自动应用代码替换建议，也不读取整个快照文件或重建旧聊天上下文。代码建议仍使用独立的「在新工作区采纳建议」流程。

## 权限与一致性

- 服务端复核当前控制者、控制版本、项目成员及运行状态。维护者需要先接管；Reviewer 可以评论，但不能借评论控制 AI。
- 只允许同一任务的讨论。替换为另一任务的话题或消息 ID 会被拒绝。人工终端不接受这类指令，避免把评论解释为 shell 输入。
- 来源由数据库读取并计算 hash，浏览器不能伪造作者、正文或代码锚点。来源信息在预览后变化时要求重新预览；发送成功后保留不可变快照。
- 消息明确标注为项目引用数据，不是系统指令、授权或审批。通过原有持久运行队列、租约和一次投递规则进入 Pi，不创建第二个 AI，不扩大工具或工作区权限。
- 提交前在当前标签页的 sessionStorage 保存原请求，包括消息 ID、来源 hash、控制版本和幂等编号。响应丢失后刷新，显式重试同一编号；已经接纳时返回原指令，不能重复投递。
- 存储不可用时不发送新的请求。该恢复范围是同标签页刷新，不承诺浏览器关闭后的恢复。投递结果未知继续沿用原指令核查，不自动重发。

## 验证

控制数据库专项覆盖多作者来源、预览不发送、选中消息按原顺序、后续回复排除、同键重试、不可变记录、来源变化、旧控制者拒绝、跨任务替换及终端拒绝。纯协议 fixture 没有实际文件，明确记录零字节用量，避免未结算预留影响后续用例；生产限额保持不变。

原生及 Docker 的真实 Pi 专项均通过本机模型协议服务，验证所选评论、原评论作者及控制者实际进入后续模型请求，原进程与工作区保留。没有外部模型推理。

双成员浏览器覆盖选择、预览、确认、丢失响应后刷新并同键重试、仅一条指令、原讨论定位、控制交接/停止以及桌面和 390px 布局。固定源码 API/权限与 SQL 测试相互补充，不把页面隐藏按钮当作授权验证。
