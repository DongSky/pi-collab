# pi-collab 本地开发与调试方案

初稿日期：2026-09-23；当前更新：2026-09-24。项目名、派生自 pi-web、使用本机 Pi 调试均已确认。原生与可选 Docker 基础后端及本机生产安装已通过主流程验收，迁移到 073。下面按开发阶段保留实现笔记；各节当时的“尚未”不代表最新状态，当前剩余项见 [逐模块收尾](module-closeout.zh-CN.md)，最新证据见 [实施状态](implementation-status.zh-CN.md)。

本文件的原始容器优先拓扑已被用户要求更新：默认采用原生 PostgreSQL/Pi 进程，Docker 不再是开发前置条件。详见 [双运行后端 ADR](adr/0006-dual-runtime.md)。

本文件补充 [主计划](development-plan.zh-CN.md) 和 [实施任务清单](implementation-backlog.zh-CN.md)。实际 PR 创建的原生流程见第 44 节；真实 GitHub 账户验收和 Docker 对等能力仍单独记录。

## 1. 已核对的本机条件

- 项目目录：`/path/to/pi-collab`。
- Pi CLI：`0.87.0`，入口为 `~/.nvm/versions/node/v22.19.0/bin/pi`。
- 当前 shell 的 Node：`v26.9.0`；npm：`11.19.1`；Git：`2.50.1`。
- Docker CLI：`28.4.0`；Docker Compose：`v2.39.2-desktop.1`。
- 核对时 Docker daemon 不可连接，需要实施容器阶段时启动 Docker Desktop；本次没有启动或修改它。
- 核对时未发现 30141、30142 端口的监听进程；每次启动前仍要重新检查。
- `psql` 和 `podman` 未出现在当前 PATH；PostgreSQL 已通过 embedded-postgres 在项目数据目录运行，不要求 Docker 或系统数据库服务。

上游 pi-web 固定 Pi SDK `0.87.0`，与本机 CLI 版本一致，有利于 P0 对照验证。但应用依赖必须在仓库锁定，不能把全局安装目录当成应用依赖来源。

当前 Node 与 Pi 安装路径所含版本不同；P0 统一 Node/npm 工具链并写入版本文件。优先验证上游要求的 Node 22.19.0 或适配的受支持 LTS，不能假设 shell 切换后仍执行同一 Node。

## 2. 派生仓库的方式

1. 保留当前 `docs/` 与 README 规划资料；P0 在临时目录获取固定上游基线，再将 Git 历史和源码安全导入当前非空目录，不能清空目录后重新 clone。
2. 建立 `upstream` 指向 `agegr/pi-web`，产品包/显示名使用 `pi-collab`；是否创建远程 GitHub fork/新仓库在需要发布远程时单独处理。
3. 保留 MIT 许可证和原始版权，README 明确派生来源与本项目增加的功能。
4. 先运行上游已有验证和本地页面，保存基线结果，再加入 `lib/collab/`、执行服务和协作数据模型。
5. 不升级或覆盖全局 Pi 安装，不把本项目的实验扩展安装到个人全局资源列表。

## 3. 本地拓扑

- 浏览器与 Next.js 控制层：`127.0.0.1:30142`，预留 pi-web 默认 `30141` 给上游对照。
- 默认 PostgreSQL：项目管理的本机进程，`127.0.0.1:55432`。执行管理、Git/model broker 默认也采用本机进程；需要宿主调试的端口仅绑定回环地址。Docker 部署时才使用容器内网。
- 用户 A、B、Reviewer：三个独立浏览器上下文，不使用“一个账户开三个标签页”代替真实多用户测试。
- 工作区 A/B/C：默认独立 Pi 进程、clone、HOME、agentDir 和会话目录；Docker 版本改用独立 Linux 容器和挂载目录。两版共用身份、任务与协调协议；恶意代码沙箱验证仅适用于隔离运行时。
- 临时测试 Git 远端：本地受控 bare repository，用于无外部账号的 push/merge 故障验证；GitHub 专有行为在独立测试仓库验证。

无 Docker 版本独立支持本机开发与功能调试；其原生进程模型面向可信成员，不能据此宣布容器沙箱隔离验收通过。共享资源 broker 的业务协议在两版均需验证，原生 shell 自行绕过 broker 的访问不属于强制隔离保证。

## 4. 开发数据与凭据

- 使用项目独立的开发数据根目录，例如 `.local/`，按组织/项目/工作区分区；将其、`.env.local`、快照和测试输出加入 `.gitignore`。
- 每个 Pi 子进程显式传入自己的 `PI_CODING_AGENT_DIR` 与 session storage；不在共享服务进程临时改全局环境模拟用户。
- 个人 `~/.pi/agent` 的会话、配置和扩展不自动加载。开发模型登录采用独立 profile，或经配置的模型网关。
- 复用现有凭据若有需要，先通过受控授权配置进入本地秘密存储；不把密钥打印到日志、命令历史、计划文档或 Git。
- 第一轮协议测试关闭自动扩展、skills 和 context 文件发现；随后逐类开启受测试资源，避免把本机插件行为误认为平台实现。
- 只做版本/帮助检查不会证明模型凭据可用。协议测试使用临时密钥和本地协议服务；真实模型验收另行授权、记录，不把协议 fixture 当作模型能力验证。

## 5. P0 应交付的启动入口

以下列出脚本契约；`dev:local`、`dev:services`、`dev:seed` 已实现，后续任务和停止入口以 package.json 为准：

- `dev:local`：启动本机控制层，绑定 `127.0.0.1:30142`；检查依赖/配置并输出状态，不隐式暴露到局域网。
- `dev:services`：启动项目专属原生 PostgreSQL，回环监听，数据保留在 `.local/`。
- `dev:seed`：幂等创建两个测试组织、用户和项目；仅在开发环境有效，不生成固定生产管理员密码。
- `test:multi-agent`：在隔离测试仓库执行三 AI 协作场景，并保存版本、运行时间、证据和失败日志。
- `dev:stop`：停止本项目进程/容器，保留开发数据；删除 volumes 作为单独显式操作。

启动前用监听端口和 PID 核对已有服务，健康则复用；不因为端口占用就杀死未知进程。应用 PID、日志和调试链接与 run/workspace 关联。

## 6. 调试递进与通过标准

1. **上游基线**：原始聊天、会话加载、终端、diff 可用；锁定依赖与版本。
2. **单用户适配**：pi-collab 调用独立 profile 的 Pi，验证流式事件、工具、取消、恢复和版本兼容。
3. **双用户隔离**：A/B 登录，各自启动 AI；同时改同名文件；相互不可读取私有组织数据，未提交代码互不覆盖。
4. **多 AI 协调**：后端、前端、数据库 AI 同时运行，演示契约、范围冲突、资源租约和组合失败。
5. **Git 整合**：本地远端先验证状态机，再验证 GitHub App、CI、PR 与保护分支语义。
6. **故障调试**：杀掉指定测试 runner、重启控制层、断开网络，检查 fencing、未知结果对账和没有第二有效执行者。
7. **共同编辑**：首版 Beta 后再加入，重点验证文档/Git/终端/AI 写入模式切换，不能只演示两人打字同步。

每一步记录输入 revision、执行环境、预期与实际结果。真实运行只使用隔离测试仓库，不把个人项目当作故障注入对象。

## 7. 已实现的账户使用流程

首次访问 `/sign-in` 时，未初始化安装会转至 `/setup`。从私有 `.local/config.json` 读取 `bootstrapToken`，填写团队名称、Owner 姓名、邮箱和至少 12 位密码。初始化不能重复执行；`dev:seed` 也会关闭初始化入口。

登录后访问 `/account` 设置验证器，验证 6 位 TOTP 并保存恢复码。Owner/Admin 邀请成员和调整组织成员角色前必须完成 MFA，不能关闭必需的 MFA。可以在账户页面撤销设备会话；被停用的组织成员立即失去旧会话和组织数据权限。

团队管理页创建绑定邮箱、48 小时有效的单次邀请链接，可同时授予项目角色。已有账户必须先登录再打开邀请；邀请不覆盖原密码、不修改已有角色、不重新激活停用成员。

密码重置页位于 `/forgot-password`。本机邮件保存在 `.local/mailbox/*.json`（0600 权限），通过其中链接完成重置后所有旧会话失效。此目录含秘密链接，不能上传日志或纳入 Git。生产 SMTP 尚需部署验证；当前没有实际向外部邮箱发送消息。

验证入口：`npm run test:collab:identity:e2e`。测试自动创建临时数据库和源码副本，使用多个独立浏览器上下文，完成后清理测试进程、数据库和副本；当前开发服务和演示账户保持可用。无 Docker 依赖。

## 8. 执行管理器与本机仓库入口

`dev:local` 现在同时启动 Web、独立执行管理器和回环模型网关（默认 `30143`），仍使用本机 PostgreSQL/Pi，不调用 Docker。执行管理器使用独立受限数据库账号；Web 与 Pi 子进程都不会收到它的连接串。单独调试执行管理器可用 `npm run dev:executor`；多个执行器会竞争领取不同的数据库租约，不靠浏览器内存决定所有权。

本地仓库的导入目前是受信任的管理员 CLI 操作，尚无仓库连接界面：

```bash
npm run repo:import -- --project <项目 UUID> --actor <项目维护者邮箱> --source <选定的本机 Git 仓库> --name <显示名称>
```

它创建项目数据目录下的独立 bare cache 并登记准确的基线 SHA，不修改原仓库，不保留 origin，也不将宿主路径作为浏览器参数。该操作以指定维护者为有效身份，并在审计详情标记 `local-administrator-cli`。导入和迁移脚本使用本机管理员配置，不能暴露为任意路径的 HTTP 接口。

已实现运行 API：按任务接纳启动（202）、按 run 请求停止（202）、查看持久状态，以及项目级 SSE/游标补发。任务页现已提供启动、输出、历史记录和停止界面；未配置项目模型时启动按钮不可用。没有模型授权的 Pi 不会被当作成功的 AI 运行。`tests/collab/execution.test.ts` 的真实 Pi 场景使用显式的诊断工具，不能代替真实模型验收。

租约失效、RPC 结果未知或退出未确认会隔离工作区并保留 `reconciling/unknown`，不自动重试或复用目录。原生退出证据对账已实现，见下方第 11 节；不要手动改数据库状态来绕过隔离。协议见 [ADR-008](adr/0008-durable-execution.md) 和 [ADR-011](adr/0011-native-run-recovery.md)。

## 9. 项目模型与网关

原生开发的 Model Gateway 绑定 `127.0.0.1:30143`，使用独立受限数据库账号；可单独用 `npm run dev:gateway` 调试。当前只支持 Responses 兼容服务的文本和本地 function 工具。Docker 模型网络、其他 Provider API、图像输入尚未验收，因此不会作为可用能力提供。

在确认要将某个个人模型开放给指定项目后，受信任本机管理员可执行：

```bash
npm run model:import -- --from-pi --project <项目 UUID> --actor <维护者邮箱> --provider <Pi provider 名> --model <model ID> --name <显示名称>
```

这只导入选中的字面量 key/模型，拒绝 shell 凭据命令、环境插值和未支持的自定义配置，不修改个人 Pi 文件。`--actor` 对应有效项目维护者；Owner/Admin 必须已启用 MFA。当前 CLI 是受信任本机管理员入口，不是可向浏览器公开的账户模拟接口。凭据 AES-GCM 密文存入网关私有表，主密钥位于 `.local/model-master.key`（0600）。Web/执行器数据库角色无法读取它；Pi 工作区只接收短期 run capability。原生同系统用户仍不构成恶意代码安全边界。

首次配置后，在任务详情下方选择仓库和模型、填写指令，点击「启动 AI」。观察者可以查看项目运行；普通开发者只能指挥自己的任务。HTTP 提交响应丢失时，使用「重试同一请求」保留原有请求编号；重试不会创建第二个运行。停止后先显示「正在停止」，确认进程退出后才显示「已停止」。

默认每次运行至多 32 次请求和 1,000,000 token，项目每天 10,000,000 token；输入上下文与输出上限先预留，再按完整终态用量结算。失败或未知响应保留预留额度。此阶段尚无货币费用核算和额度管理界面；不要将 token 限额表述为准确费用预算。更多限制见 [ADR-009](adr/0009-model-gateway.md)。

当前 `test:collab` 中的网关测试使用确定性本地 Responses 服务，覆盖真实 Pi 流式工具往返，不消耗外部模型额度。浏览器运行界面测试并入 `test:collab:identity:e2e`，安全截图位于 `test-results/collab/run-ui*.png`。真实模型并行场景仍需单独验证。

## 10. 项目成员、任务交接与应急接管

项目维护者可在项目概览点击「管理项目成员」，将已有团队成员按邮箱加入项目，修改角色或关闭「项目访问」。停用采用保留记录的方式，历史任务、运行和审计仍可由获授权成员查看。项目不允许通过成员管理移除最后一位有效维护者；组织停用仍优先执行，出现无人管理的项目时使用应急接管。

成员修改带版本检查：其他标签页已保存更新时，旧表单会提示刷新，避免覆盖新权限。任何实际角色/访问修改会停止该成员在本项目的排队与活动运行，旧模型凭证与实时连接失效；其他项目资格和登录会话保持各自的授权状态。重新启用成员不会恢复旧运行。

「任务交接」把负责人转给已启用的开发者/维护者，先请求旧运行停止。新负责人需要重新发起运行；工作区 `reconciling` 时仍须先对账，不能靠重新分配绕开隔离。项目审计页可查看操作人、时间和变更详情，并加载更早记录。

组织管理页提供「项目治理与应急接管」。组织 Owner/Admin 在未加入项目时只看到治理元数据；输入至少 10 个字符的原因并通过既有 MFA 要求后，可显式取得项目维护者资格。原因进入项目审计，不能以组织管理员身份直接跳过内容授权。

验证：`tests/collab/project-members.test.ts` 覆盖真实数据库竞争条件和真实 Pi 停止；`test:collab:identity:e2e` 包含完整项目成员浏览器流程，截图为 `test-results/collab/project-members*.png`。协议及尚未交付的运行恢复边界见 [ADR-010](adr/0010-project-membership-lifecycle.md)。

## 11. 异常运行对账与归档

任务显示「待对账 · 工作区已隔离」时，项目维护者可以填写至少 10 个字符的原因，点击「检查旧进程并解除阻塞」。这是持久请求，由本机执行器处理；浏览器关闭不取消请求。Owner/Admin 沿用 MFA 要求，申请后撤权或重新授权都不能使旧请求继续有效。

界面会显示等待处理、旧进程仍存活、缺少记录等结果。正在运行的旧进程由原执行器的停止/租约看门狗处理；对账入口只观察，不按磁盘记录的 PID 杀进程。证据不足时继续隔离，可在原因消除后重新申请。原生回执位于 `.local/runtime-receipts/`，不要编辑它来解除隔离。

对账成功只证明旧写入者已退出，原工具/外部服务结果仍可能未知。运行被标记为已停止，原 `unknown` 命令不改为成功。维护者/任务负责人显式发起下一次运行时，会创建新目录和新权限；默认使用仓库基线，也可先保存快照后按下方第 12 节显式恢复。

停止后的运行允许维护者填写原因并「归档工作区」。归档保留代码、输出和历史，记录至少 7 天保留期；当前没有自动物理删除，不会在第 7 天丢弃文件。后续回收必须先实现引用检查与快照保留策略。

支持 macOS/Linux 的受信任原生运行。旧版没有回执、启动中断间隙、系统启动标识变化或数据迁移到其他节点的情况仍保守隔离；管理员处置流程和 Docker 对账尚待完成。验证入口为 `tests/collab/recovery.test.ts` 和完整浏览器测试；截图为 `test-results/collab/run-recovery*.png`。

## 12. 保存交接快照并接续代码

运行停止后，任务负责人或项目维护者可在「任务交接快照」填写已完成工作、剩余事项、环境依赖和建议重新执行的验证命令，再点击「保存交接快照」。执行器核验退出证据后保存代码，刷新或关闭浏览器不会丢失请求。响应不确定时使用「重试同一快照请求」，避免重复申请。

快照就绪后检查变更与排除清单，可下载完整 JSON 清单。原提交与快照基线分别显示：快照采用经过排除规则处理的新 Git 历史，保留原始 SHA 作为来源，不复制原 `.git`、HOME、Pi 会话或密钥。默认排除疑似秘密、生成文件、符号链接、子模块及超过 2 MiB 的文件；规则不是完整秘密识别保证。每层最多 5,000 个文件、唯一内容总计最多 64 MiB。未解决冲突、稀疏/暂存意图等特殊索引会明确报错。

接手人在「恢复来源」选择快照，核对当前指令与项目模型后点击「启动 AI」。恢复使用新工作区、新用户授权与新模型凭据，保留暂存/未暂存修改和未跟踪状态，旧文件保持原样。再次保存时记录前一快照 ID 和 hash。旧版执行器不能领取它不理解的恢复任务；混合升级时此类任务等待新版执行器。

快照不自动重放工具操作，也不代表测试已通过。进程、外部数据库/服务、安装依赖和原 Git 祖先未捕获；接手人须重新验证，可使用下方独立验证入口。当前只支持同任务同仓库的原生运行，Docker 恢复、完整索引格式、完整环境复现与保留回收仍需完善。

私有数据位于 `.local/snapshots/`。不要编辑已发布 manifest/blob；恢复前校验失败会阻止 AI 启动。迁移、备份和回收必须保留数据库引用及这些文件。协议见 [ADR-012](adr/0012-workspace-snapshots.md)。验证入口为 `tests/collab/snapshot-storage.test.ts`、`tests/collab/recovery.test.ts` 和完整浏览器测试；截图为 `test-results/collab/snapshots*.png`。

## 13. 对固定快照执行验证

任务详情的「快照验证」由维护者创建仓库专属配置版本。每步选择 Node.js 或 npm，参数每行一个，超时 1–600 秒；最多五步，按顺序执行，首个失败后停止。配置保存后不能改写，调整时创建新版本。例如有锁文件的 npm 项目可以先配置 npm 的三个参数 `ci`、`--ignore-scripts`、`--no-audit`，再新增 npm 的 `test` 步骤；实际安装选项与依赖脚本要求由维护者确定。

任务负责人或维护者选择就绪快照和配置，点击「执行快照验证」。本机执行器自动创建新的独立工作区运行命令，不消耗模型额度，不需要 Docker，也不复制个人 HOME、数据库/模型凭据或原工作区安装的依赖。本机命令只能面向可信项目；外网和外部数据库并没有因此获得隔离。

「指定检查通过」只表示这份配置对该快照的实际工作代码执行成功。命令返回非零值、超时、残留子进程、输出超过 1 MiB 或修改快照代码时，不会通过。可以下载包含清单哈希、工作代码 SHA、配置、环境指纹、退出码和清理状态的证据；原始输出不保存，当前诊断信息有限。新的快照、修改后的配置、其他候选组合都需要新证据。

浏览器断开不取消验证；停止按钮请求当前执行器终止并确认进程退出。响应丢失时使用「重试同一验证操作」。撤权、重新授权、任务交接后，旧申请不再有效。执行器或数据库失联时显示「验证结果待核查」，保留工作区、限额占用和可能的外部影响，不自动重试。验证专用的人工对账入口尚待实现，不能通过修改数据库状态绕过此限制。

每个执行器额外运行一个验证作业，项目最多两个、申请人最多一个；未知结果继续占用名额。工作文件位于 `.local/workspaces/<验证 UUID>/`，启动标记和本地证据位于 `.local/validation-executions/`。尚无自动回收，部署前需规划磁盘保留。环境指纹不等于可重放的完整系统镜像，Docker 验证和整合准入策略仍未完成；固定版本依赖见下节。

验证入口：`tests/collab/validation.test.ts`；浏览器流程并入 `npm run test:collab:identity:e2e`，安全截图为 `test-results/collab/validations*.png`。协议见 [ADR-013](adr/0013-snapshot-validation.md)。协作测试最多同时运行两个测试文件，避免多个隔离数据库耗尽同一本机 PostgreSQL 的连接；每个测试内部的并发领取和请求竞争仍真实执行。

## 14. 发布成果并锁定下游输入

完成快照验证后，在「任务成果与依赖版本」选择依赖当前有效的验证记录，填写下游可用的接口、文件与限制，点击「发布成果版本」。负责人或维护者可操作，Owner/Admin 需要 MFA。每次发布生成新的编号版本，保留快照和证据链接；不会自动把任务标为完成、可合并或已合并。

严格依赖等待上游发布成果，单纯把上游任务标为完成不再满足条件。提交运行时已存在的成果会立刻锁定；缺少的严格输入在实际领取时锁定。软依赖可以先开发，但缺失输入的旧运行不能发布成果，即使上游后来已有结果也要新建运行并重新验证。

AI 在 `../dependencies/<上游任务 UUID>/` 读取独立代码副本，在 `../dependencies/inputs.json` 查看锁定版本。它们不直接合并进自己的代码，也不是另一个 AI 的工作目录。最多 32 个直接依赖；副本合计最多 20,000 个文件、128 MiB。复制失败或内容损坏会在 AI 启动前报错；不要手动改动这些输入。

上游发布新版、撤回成果或调整依赖图时，下游保留原代码与输入，界面会显示「依赖需要重新验证」。先保存当前代码，再显式启动新运行取得当前输入，随后重新执行验证和发布。撤回要求填写原因，历史记录与被引用版本保留；已锁定被撤回版本的排队运行不会自动切换，应停止后重新提交。

当前只提供直接源代码输入，尚不自动安装上游包、运行外部服务、展开所有传递依赖或合并分支。通过指定检查不代表组合、契约或评审已通过；这些能力仍按开发计划继续实现。Docker 的依赖输入尚未验证，相关启动会被拒绝。

升级时先迁移再重启新执行器。旧执行器不能领取新协议运行或带依赖的捕获/验证任务；旧运行未记录依赖版本，不能把其旧证据直接发布为成果。旧版已排队的依赖任务需停止后重新提交。协议见 [ADR-014](adr/0014-immutable-task-results.md)，测试见 `tests/collab/task-results.test.ts` 和完整浏览器流程，截图为 `test-results/collab/task-results*.png`。

## 15. 声明范围、查看重叠与核对实际代码

运行处于排队、准备、执行或等待输入时，当前运行的负责人或维护者可在「修改范围与重叠告警」中声明相对路径，每行一项。例如 `src/api/` 包含目录及子目录，`src/types.ts` 只匹配该文件；不支持通配符。填写变更类型和说明，可以补充符号/API 标识与预计完成时间。扩大范围时保存新版本，原声明继续保留。

同项目同仓库的其他任务若有路径或接口标识重叠，会显示具体任务与声明版本。没有重叠告警不等于没有语义冲突；尚未声明的任务不在匹配范围内。告警不锁文件、不暂停其他 AI，也不授予额外权限。另一位授权成员可在自己的浏览器查看声明和告警。

并发保存不同修改会提示版本冲突；先「载入最新声明」，再重新编辑。网络中断时「重试同一范围声明」沿用原请求，避免重复版本。运行结束后不允许补报，新运行须重新声明；人和 Pi 的受控声明共用版本规则，AI 工具见第 17 节。

保存就绪快照后，点击「核对快照范围」。报告独立核对快照最终工作代码与导入时仓库基线，包括本地提交、暂存/未暂存结果、未跟踪文件、删除与执行位变化，并列出未声明修改。恢复过的代码仍对照原始仓库基线。排除路径明确标为未核对，原始内容不会下载；中途写入后还原的操作不属于此快照比较。

「下载范围证据」包含快照 hash、基线 SHA、工作代码 SHA 和声明版本。需要保留 `.local/repositories/` 与 `.local/snapshots/` 的对应对象；损坏或缺失会返回不可核对，不能当作通过。报告不赋予成果发布或合并资格。界面上限、升级与验收边界见 [ADR-015](adr/0015-work-intents.md)。

## 16. 发布接口契约与确认 mock

在生产任务的「接口契约与确认」中展开提案表单，选择仓库，填写稳定标识、标题、接口定义、兼容策略与迁移说明。可以提供 JSON mock 示例并选择额外受影响任务；依赖图中的下游和已有消费者会自动加入。定义支持文本、JSON Schema JSON 和 OpenAPI JSON，当前仅检查格式，不自动证明接口兼容。

每个受影响任务的负责人，在自己的任务页面填写确认说明后选择确认或拒绝。全部有效确认后，生产任务负责人或维护者可发布版本。维护者若需要裁决缺少或拒绝确认的情况，必须填写至少 10 个字符的原因；裁决与负责人确认分别保存和展示，不把两者混为一谈。

提案不可直接改写，修订时选择原契约并提交新提案。破坏性修改必须说明迁移方式。提案期间依赖图扩大，或其他提案已发布新版，会阻止旧提案发布。负责人交接、角色/权限变化会使待发布提案上的旧确认失效，需要当前负责人重新确认。已发布版本保留当时的决策证据。

新运行把当前契约与 mock 固定到 `../contracts.json`，使用独立副本。运行期间上游发布新契约，不会替换其工作文件；界面会要求重新验证。保存快照后，在新运行中取得当前版本，再执行验证和发布成果。旧验证的历史通过记录继续保留，但不能用于当前版本的成果发布。

已确认 mock 只是示例数据，不能替代真实依赖、测试或人工评审。缺少真实软依赖的运行仍不能发布成果。范围声明与契约提案目前由人操作；Pi 受控协调工具、自动接口兼容分析和整合队列继续按计划实现。

本功能默认无需 Docker。升级时先应用迁移 012，再重启新版执行器；旧执行器不领取带契约输入的运行/快照/验证。测试入口为 `tests/collab/contracts.test.ts` 和完整身份浏览器流程；协议与限制见 [ADR-016](adr/0016-contract-revisions.md)。

## 17. Pi 协调工具与任务说明

原生执行器为每次 Pi 运行显式加载四个受限工具：`collab_get_context`、`collab_declare_intent`、`collab_propose_contract`、`collab_send_note`。普通项目扩展仍不自动加载。启动时若受管扩展未注册成功，运行明确失败，不带着缺失的协作工具继续开发。

在任务的「任务协作说明」中选择目标任务，提交问题、发现、阻塞或交接。对方在自己的任务中看到来源成员，以及该记录是成员提交还是某次 AI 运行提交。刷新或丢失响应重试不会生成重复说明。历史引用的契约版本可下载；说明本身不等于验证通过。当前表单创建无附件说明，带版本引用的说明可通过受限工具或授权 API 提交。

AI 启动与安全步骤间使用 `collab_get_context` 读取上下文；每页返回五条说明，按 `nextNoteSequence` 继续读取。AI 只能向依赖相邻、共享契约或最近运行使用同仓库的同项目任务发送说明。契约提案仍需负责人确认。说明不会直接给另一个 AI 插入指令，也不保证对方模型何时读取。共享资源与成果发布工具还未开放。

所有调用都检查当前运行租约/权限；每次运行最多 200 次成功修改，每位成员在同一项目每分钟最多 20 条说明。超时或响应丢失时保留原 `idempotencyKey` 和内容；不能把未知结果当失败而换编号反复提交。无 Docker 仍为默认版本；Docker 协调工具尚未验收。协议、限制与测试见 [ADR-017](adr/0017-run-scoped-coordination.md)。

## 18. 受管理 PostgreSQL 测试资源

`npm run dev:local` 现在同时启动资源 broker；默认仍无需 Docker。更新代码后应用迁移 014–015，再重启服务。已应用的迁移不修改。配置升级自动增加专用 broker 数据库账户，资源密钥单独保存在 `.local/resource-master.key`（0600）；已有资源而密钥丢失时不重新生成替代密钥。

维护者在任务页「受管理测试资源」创建命名资源。每项资源有独立 PostgreSQL 角色和 schema。AI 使用 `collab_request_resource` 一次申请所需资源，在 `collab_get_context` 取得 request ID 与 fence，再用 `collab_execute_resource` 提交单条 SQL。每次 SQL 在独立事务中执行，任务终端不接收数据库密码。等待批次不占部分资源；同一运行不能拿着一批资源再等另一批。

AI 可使用 `collab_cancel_resource_job` 和 `collab_release_resource`。运行发起者可在资源面板取消自己的 SQL 作业或释放租约；维护者可管理项目内所有作业，并停用/恢复资源，每次填写原因。停用取消相关等待批次并阻止新申请，旧写入者退出前不能恢复；恢复保留测试数据，不复活旧批次。取消/释放本身不停止 AI，AI 可重新申请资源。成员也可通过运行面板停止 AI，平台随后停止 SQL 并释放资源。释放请求不等于已释放；界面显示「等待旧作业退出」时，不会把资源交给下一运行。结果未知的 SQL 不自动重跑，应先检查实际数据。SQL 已提交只说明该作业，不代表代码验证或整合通过。

每个项目最多 16 项资源，一批最多 8 项，每次运行最多 100 个 SQL 作业；SQL 超时 20 秒，结果最多 100 行/64 KiB。测试资源属于可信本机环境，自动数据库/端口隔离、资源重置/删除、独立实例配额和其他外部环境仍待实现。详见 [ADR-018](adr/0018-managed-postgres-resources.md)。


## 19. 本地 Git 整合预演

应用迁移 016 后重启 `npm run dev:local`，原生执行器会领取整合预演，仍不依赖 Docker。任务页的「项目 Git 整合队列」对项目内已发布成果开放：选择仓库、维护者创建的组合验证配置和成果，平台自动补齐同仓库依赖并固定执行顺序。每个预演最多 32 项成果，每项目最多 20 项活动预演。

同一目标分支串行组合。独立任务仍可继续运行，原任务目录和导入仓库不会改变。Git 冲突记录具体来源成果及 base/ours/theirs；组合成功后在另一新工作区执行配置中的真实检查。配置应检查组合后的项目，不应假定源任务的独立 `../dependencies` 目录仍存在。

查看整合证据可核对输入集合、Git 候选提交、实际受检快照、排除路径、命令/环境指纹与退出证据。源成果撤回/新版、依赖/契约或目标变化会使旧结果失效；重新组合必须创建新预演。取消须填写原因，开发者可取消自己发起的预演，维护者可取消项目内预演。

「组合检查通过」只认证所列快照与配置；正式规则和人工评审请继续按第 20 节操作，检查通过本身不等于评审或合并通过。预演本身不会更新目标分支；受控本地推进见第 23 节。秘密路径/生成目录等排除内容不在验证范围内。失联整合保持 unknown 并阻塞该目标，不自动重跑命令，目前尚无人工解除入口。协议和后续工作见 [ADR-019](adr/0019-local-integration-previews.md)。


## 20. 必跑规则与版本评审

应用迁移 017 后重启本机服务；默认仍无需 Docker。维护者在「项目 Git 整合队列 → 维护者：设置整合规则」选择仓库和必跑验证配置，设置 1–3 位独立批准、Reviewer 角色的批准是否计数，并填写规则变更原因。所选配置的全部步骤都必须成功。规则不可原地改写，每次发布保留新版本；没有规则的旧预演不能获得正式评审。

有规则的仓库会固定选择必跑配置。新建整合会锁定当时的规则，来源代码和目标基线也保持固定。其他维护者同时修改规则时，旧表单提交会冲突；重新加载规则再编辑。发布新规则会使旧组合检查和评审失效；运行中的旧检查会停止，不能把旧证据重新标记成新规则的证据。

组合检查通过后，Maintainer、Developer 或 Reviewer 可展开「提交版本评审」。先核对「查看整合与评审证据」中的固定代码、排除范围、检查和规则，再开始评审、填写说明并选择批准或要求修改。整合申请人、所有来源运行发起人和成果发布人不能批准此组合；依赖来源也纳入计算。Reviewer 的批准按规则计数，提出的修改要求始终阻塞。

同一个评审者可以更新或撤回自己的决定，所有历史保留。另一个窗口先保存后，旧窗口必须重新开始评审；网络响应丢失时用「重试同一整合操作」继续原请求。成员被停用、改变角色或重新授权后，旧批准不再计数，须重新评审。停用成员不会自动消除其修改要求；由本人恢复授权后更新决定，或基于新候选重新评审。当前没有维护者强制清除异议入口。

满足条件后显示「检查与评审条件已满足 · 可申请本地推进」。此状态不会更新 Git 分支，也不能作为长期有效的合并令牌。排除的内容和未封装环境仍未验证；固定代码差异与冲突浏览见第 21 节；冲突修复见第 22 节、受控本地推进见第 23 节；外部 PR/CI 尚待实现。证据下载包含所绑定的规则与最近 100 条评审历史，数据库保留完整历史。详见 [ADR-020](adr/0020-required-checks-and-reviews.md)。


## 21. 查看固定差异与三方冲突

在有 Git 候选或冲突证据的整合卡片中展开「查看固定代码差异与冲突」，点击「读取代码文件列表」。Maintainer、Developer、Reviewer 和 Viewer 均可读取其项目内的记录，不需要终端权限。每页最多 100 项，可以继续读取下一页；文件选择必须使用当前列表对应的差异 hash，不能用文件路径读取任意本机文件。

组合成功时，查看相对于原目标基线的新增、修改、删除和权限模式变化。选择文件后显示逐行差异，可以展开两侧完整文本，并核对字节数、Git blob、SHA-256 与换行格式。代码来自保存的 Git 对象和受检快照，正在运行的 AI、后来的 HEAD 或工作文件变化不会改变历史差异。重命名目前表示为删除和新增。

发生 Git 冲突时，选择冲突文件查看 base、ours 和 theirs。base 是共同基线，ours 是此前已组合的代码，theirs 是本次来源成果。不存在的一侧会明确显示；此时没有完整候选，也没有组合检查通过的含义。阅读不会自动创建修复、写入任一 AI 工作区或消除冲突。

每侧文本最多 256 KiB、8,000 行；二进制、不支持的编码和超限内容只展示可用的身份信息，并明确说明未完整展示。秘密路径、生成内容、符号链接等排除项也保留说明。删除前的历史内容同样经过秘密模式筛查；筛查规则不能保证识别所有秘密。HTML 只显示为文字，不执行。不可见控制字符显示为 ⟦U+…⟧，hash 始终对应原始字节。

旧成果或规则失效后，有权限的成员仍能查看历史代码，但不能沿用旧批准。对象或快照损坏、路径不安全或权限撤销时，读取会被拒绝。每个 Web 进程最多同时读取两份代码证据，繁忙时稍后重试。界面阅读不等于完成评审，仍需按第 20 节提交决定；冲突修复见第 22 节；评论锚点与建议补丁继续开发。技术边界见 [ADR-021](adr/0021-immutable-integration-code-review.md)。

## 22. 创建、运行与发布冲突修复任务

在当前有效且绑定必跑规则的冲突整合卡片中展开「创建冲突修复任务」。开发者可分配给自己，维护者可选择有开发权限的成员；填写任务名称与修复目标。网络响应丢失时使用「重试同一修复请求」，不会创建第二个任务。任务负责人仍可经正常项目管理入口显式交接。

打开修复任务后，「固定冲突修复来源」显示原整合、目标、每个成果版本与当前有效性。依赖图固定，仓库与必跑配置不可更换。每次运行使用独立原生工作区，复现原冲突并继续组合首次冲突之后的全部成果。每个冲突步骤保留三方对象、模式和类型；二进制临时选边或干净 Git 索引不代表修复成功。原任务、失败预演和导入仓库不被改写。

AI 须读取工作区外的 `resolution.json`；首次运行另有 `resolution-evidence.json`，始终标记待修复。修复后保存交接快照，执行锁定的必跑验证。验证会先拒绝残留文本冲突标记，再执行命令并复核代码与固定来源；UTF-8 和两种字节序的 UTF-16 均检查。文档中的字面冲突标记需明确转义或编码；标记消失不能证明二进制、重命名、删除或语义选择正确。快照恢复仍使用新工作区和同一来源链。

发布时必须勾选「确认所有冲突选择」，并说明核对结果。发布后在整合队列中选择修复成果，它替代原始完整组合；不要同时勾选被覆盖的原成果。系统拒绝重复覆盖，保留原作者及嵌套修复来源；下游依赖会按覆盖关系重新排序。新组合仍需必跑检查和新的独立评审，原作者和修复作者都不能批准自身组合。该步骤不会推进目标；本地推进另按第 23 节执行。

原始来源撤回/更新、目标或规则改变、原整合申请人撤权等会使旧修复失效。正在运行的修复经心跳停止，旧验证不能用于新发布；重新授权也不会恢复原申请人的旧授权版本。请从新的整合重新创建修复任务，不能靠重试改用最新输入。

升级顺序：先 `npm run db:migrate` 应用 018，再部署 web 并重启新执行器。旧执行器跳过修复及直接消费修复快照的运行/捕获/验证/组合；包括先排队、后等到修复成果发布的严格依赖。无修复来源的旧工作继续兼容。已经应用的迁移不可修改，修复来源不可为降级而剥离。

验证入口为 `node_modules/.bin/tsx --test tests/collab/resolution-runtime.test.ts tests/collab/resolution-tasks.test.ts` 和 `npm run test:collab:identity:e2e`。它们使用临时数据、真实 Git 和本机 Pi 诊断，不需要 Docker，不读取个人模型凭据，也不调用外部模型。截图在 `test-results/collab/resolution-*.png`。Docker 修复运行暂被拒绝；通用未知副作用对账仍待实现，本地目标推进见第 23 节。边界见 [ADR-022](adr/0022-conflict-resolution-workspaces.md)。

## 23. 本地 Git 推进与终态对账

默认仍使用本机 Node、Git 和 PostgreSQL，无需 Docker。先运行 `npm run db:migrate` 应用 019，再重启 Web 与新执行器。PostgreSQL 需要可安装的 `pgcrypto` 模块，本机 bundled PostgreSQL 已验证具备；迁移在私有 schema 安装。旧整合执行器在升级后也会避开待推进/待对账目标，但不能处理新推进任务。

有必跑规则、当前检查和独立批准的整合卡片中，启用 MFA 的 Maintainer 可展开「推进本地 Git 基线」。核对分支、完整目标/候选 SHA、固定代码与排除范围，填写原因并勾选确认，再提交。最终提交与候选同代码树，多一个固定溯源提交，因此 SHA 不同；申请记录显示它的完整 SHA。原基线中的排除路径只允许原样保留，内容未被本次检查。

平台只更新导入的 bare 仓库，不更新原始导入来源、个人工作区或远程仓库。每个目标串行推进；执行前重新检查原申请权限版本、MFA、输入、规则与确切评审。新基线会出现在仓库选择和项目事件中。其他 AI 在读取协作上下文时可看到基线变化，已有工作区不会被自动 rebase，新组合须在新目标上重新检查。

请求成功但响应丢失时，用「重试同一整合操作」继续原请求。点击「请求停止推进」不代表 Git 已取消；终态回执确认后才释放占用。显示「推进结果未知」时，维护者填写原因并「申请 Git 对账」：只确认已发生的推进，或封闭尚未执行的操作，不会重复应用。Git 写入与 SQL 回执不同时发生，失联/超时不能当作未执行。

「目标分支异常 · 保持占用」表示实际 Git 或数据库基线偏离固定输入，须本机管理员检查；当前没有自动重置、采纳外部分支或强制释放入口。维护者重复对账不会掩盖偏离。普通成员可下载证据，不获得推进权限。任务完成状态仍由任务流程决定，不随本地推进自动改写。

验证入口：`node_modules/.bin/tsx --test tests/collab/promotion-runtime.test.ts tests/collab/promotions.test.ts` 和 `npm run test:collab:identity:e2e`，均使用临时数据和真实 Git/本机 Pi 诊断，没有外部推理。浏览器截图为 `test-results/collab/promotions*.png`。实际进程终止、TCP 断连及 COMMIT 回应丢失测试不等于硬件断电验证。远程 GitHub/PR/CI 交付、Docker 推进对等能力与灾难恢复仍待实现。见 [ADR-023](adr/0023-local-promotion-decisions.md) 与 [ADR-024](adr/0024-durable-local-promotions.md)。

## 24. GitHub App 登记与只读仓库关联

这一阶段仍无需 Docker。应用迁移 020 后，可登记 GitHub App、保存与本地导入仓库一致的远端读取记录，并在团队管理中停用关联。迁移 022 的新仓库远程导入见第 26 节；已有仓库原生同步见第 27 节；push、PR 或远程合并仍未完成。不把关联成功当作完整 GitHub 交付验收。真实 GitHub App 验收需要操作者自行准备相应安装，本项目测试只使用隔离 HTTP 服务与临时 RSA 密钥。

在 GitHub 创建并安装 App，为准备读取的仓库授予 contents 读取能力，记录 App ID、Installation ID 和所属账户的数字 ID。私钥文件必须由当前本机操作者拥有、权限为 0600、不是链接且不超过 16 KiB。命令只读取显式指定的私钥，不扫描个人 `gh`、SSH、Git 或 Pi 配置，不接受自定义 API 主机。

先登记团队安装，`--actor` 必须对应团队中启用 MFA 的 Owner/Admin：

```bash
npm run github:import -- register \
  --organization ORGANIZATION_UUID --actor administrator@example.com \
  --app APP_ID --installation INSTALLATION_ID --account ACCOUNT_ID \
  --private-key /absolute/private/github-app.pem \
  --reason '为该团队登记并核验指定 GitHub App 安装。'
```

命令先打印请求 UUID；若响应丢失，追加 `--request-id 原UUID` 并保留其他字段重试。输出仅包含关联 ID、版本和状态。私钥加密存于数据库私有 schema，主密钥为 `.local/git-master.key`；已有连接时缺失/错误主密钥会拒绝访问，不能用重新生成文件冒充恢复。备份须同时保全数据库与主密钥，并按秘密资料管理。

已有本机仓库可先通过 `repo:import` 导入，再关联远端；`bind` 本身不会获取远程代码。只有本地当前默认分支和 SHA 与 GitHub 观察到的默认分支/提交相同时才能关联，`--actor` 须为该项目启用 MFA 的 Maintainer：

```bash
npm run github:import -- bind \
  --repository LOCAL_REPOSITORY_UUID --connection CONNECTION_UUID \
  --github-repository GITHUB_NUMERIC_REPOSITORY_ID \
  --actor maintainer@example.com \
  --reason '核对本地导入基线后关联指定 GitHub 仓库。'
```

每次远端读取只申请该仓库的只读短期令牌并在读取后撤销；不缓存到浏览器、Pi 或本地 Git 配置。安装归属、权限或本地授权版本变化时，正在进行的核验不能落库。失联不会自动重试令牌创建；进程在收到令牌前崩溃时只能等待提供方令牌过期，这不等于发生了仓库写入。

任务运行区域显示「GitHub 仓库关联」，明确区分核验时远端 SHA 与当前本地 SHA。仓库名称/链接不是身份主键，固定 repository ID 才是；记录时间之后远端可能已变化。当前不根据分支的 `protected` 布尔值授予自动合并能力。

在「团队管理 → GitHub 安装管理」填写原因并停用关联，操作要求管理员 MFA，具有版本检查和同请求重试。所有相关仓库会显示停用状态，本机副本与任务保留；这不卸载 GitHub 网站上的 App。安全恢复/密钥轮换/重新绑定尚待后续受控流程，不提供跳过核验的重新启用开关。

## 25. 协作通知与运行输出的并发修正

迁移 021 修正两名 AI 交换协作说明时，通知事件与另一运行保存输出之间的数据库死锁。运行记录改用允许外键引用的写锁，仍保留状态写入互斥、工作区租约和 epoch 检查；不会通过重试 AI 或工具操作掩盖未知结果。升级运行 `npm run db:migrate`，无需 Docker，无需重新生成工作区。

`tests/collab/coordination.test.ts` 使用真实 PostgreSQL 连接和确定性锁屏障重现竞争：修复前收到 `40P01`，修复后通知与输出均持久化成功。屏障仅存在于临时验收数据库。原本处于待核查的运行仍须走正常对账流程，不能凭这次升级直接改为成功。详见 [ADR-026](adr/0026-run-reference-locks.md)。

## 26. 从 GitHub 直接导入新仓库

运行 `npm run db:migrate` 应用迁移 022，使用第 24 节已经登记的安装连接。默认原生版本可直接下载真实 Git 历史，不需要预先手工 clone 或启动 Docker：

```bash
npm run github:import -- import \
  --project '<项目 UUID>' --connection '<安装连接 UUID>' \
  --github-repository '<GitHub 仓库数字 ID>' --name '团队代码仓库' \
  --actor 'maintainer@example.com' --reason '核验默认分支并导入项目开发基线。'
```

该账号须是项目的当前 Maintainer 并启用 MFA；安装属于同一组织。命令先输出请求 UUID。响应丢失或显示结果未确认时，保持全部参数不变，并添加 `--request-id '<原请求 UUID>'` 核查原操作。仍有执行者时返回 busy；完成时返回原仓库；完整回执可恢复数据库登记而不重新联网。缺少回执、文件损坏或授权版本变化会拒绝登记。明确失败后若要重试，使用新的请求编号；失败目录保留且不复用。

项目任务页的「GitHub 仓库导入」显示最近 20 次导入，所有可读项目成员看到相同的持久状态。成功的仓库可在「运行仓库」选择，用独立工作区启动 Pi。导入只固定当时默认分支的原始 SHA 与可达 Git 历史；不获取其他分支、标签、Git LFS 附属文件或子模块仓库，也不把远端分支的 `protected` 标志当作合并许可。更新已有仓库的远端基线使用第 27 节的受控同步流程。

远程数据通过受控的单仓库只读令牌获取，Git/Pi 不持有 GitHub 凭据。单次读取上限 180 秒、传输总量 256 MiB；目录完整性检查上限 50,000 项与 512 MiB。本机版本面向可信项目，这些边界不等于恶意代码资源沙箱。凭据主密钥仍是 `.local/git-master.key`，恢复时必须保留原密钥；不要编辑 `import-ready.json` 或手动把未确认状态改为成功。未完成目录尚无自动回收策略。

验证入口为 `tests/collab/github-pack.test.ts`、`github-import.test.ts` 与完整隔离浏览器流程；使用真实 Git smart HTTP、真实 PostgreSQL/Pi 和临时 App 密钥，没有外部模型或真实 GitHub 账号调用。协议与恢复边界见 [ADR-027](adr/0027-managed-github-imports.md)。

验证入口：`node_modules/.bin/tsx --test tests/collab/github-client.test.ts tests/collab/github-connections.test.ts` 与 `npm run test:collab:identity:e2e`。浏览器截图为 `test-results/collab/github-*.png`。协议、权限和未完成边界见 [ADR-025](adr/0025-github-installation-observations.md)。

## 27. 同步已有 GitHub 仓库（默认原生运行）

应用迁移 023 后，本机管理员可按项目中启用 MFA 的 Maintainer 身份发起同步，不需要 Docker：

```bash
npm run github:import -- sync \
  --repository '<本地仓库 UUID>' --actor 'maintainer@example.com' \
  --reason '获取远端更新，只在可快进时推进公共基线。'
```

命令先输出请求 UUID。响应丢失时保留全部参数并追加 `--request-id '<原请求 UUID>'` 核查，不能用新编号绕过占用。首次执行只获取已核验默认分支；相同、远端领先、本地领先、双方分叉、远端默认分支变化会分别记录。只有远端领先且可快进时更新本地公共分支，保留远端原始 SHA。已有 AI 工作区仍固定在原版本，新运行使用新基线；旧整合须重新满足当前目标检查。

项目的「GitHub 仓库同步」展示最近 20 次记录。更新中或待核查状态不代表失败，也不会释放该目标给另一同步/整合/推进操作。未完成下载及所有不确定目录保留，当前没有自动回收。操作没有写入意图时，同键核查会终止遗留下载，不自动重启；有持久写入意图时，只确认已经达到的新目标或写入终止标记，绝不重试分支更新。

原操作人被撤权、安装停用，或需要另一维护者接手时，可以按记录编号核查：

```bash
npm run github:import -- reconcile \
  --job '<同步记录 UUID>' --actor 'another-maintainer@example.com' \
  --reason '核对失联同步的实际 Git 状态并终止未执行操作。'
```

接手人须是当前项目 Maintainer 并启用 MFA。此命令不需要 GitHub 主密钥、不联网，也不授予新的分支更新权限。发现 Git/数据库基线不一致会继续保持占用，不能手工改状态当作成功或盲目重置分支。本机模式的保证依赖平台内受控写入；同一 OS 账号直接修改托管仓库不在隔离保证内。fetch 的标签/LFS/子模块限制与第 26 节相同。

验证入口：`tests/collab/github-sync-git.test.ts`、`github-sync.test.ts`、`promotions.test.ts` 和完整隔离浏览器流程。详细协议见 [ADR-028](adr/0028-native-github-sync.md)。同步的 Git broker/Web 提交见第 28 节；选择性提交确认、push/PR/CI、安装轮换和真实外部账户验收仍未完成；Docker 仍是可选且未验证的部署方式。

## 28. 浏览器发起 Git 同步与独立后台服务

应用迁移 024 后，默认 `npm run dev:local` 会启动独立 Git 服务，仍不需要 Docker。已有 Web 服务无需为此中断时，可在另一个终端运行 `npm run dev:git`；它通过开发启动器把受限 Git 数据库角色传给服务子进程，不把管理员、Web、模型或资源服务凭据传入。停止这个独立终端时用 Ctrl+C；下一次完整启动开发服务会自动包含 Git 服务，不必重复启动。

先按第 24–26 节登记安装并导入仓库。在任务页选择关联仓库，项目 Maintainer 可在「GitHub 仓库同步」填写原因、确认当前公共基线并勾选允许安全快进，再提交「获取远端并安全快进」。账号须启用 MFA。页面基线在提交前变化时会拒绝旧请求，需要重新确认。提交成功只是持久排队；浏览器可关闭，后台继续执行。

取消和核查也在同步记录中填写原因并提交。取消可能需要等待当前读取和凭据撤销结束；已经确定完成的更新不会倒退。若显示「执行已中断，等待维护者核查」，另一名当前维护者也可提交「核查原同步」。核查只确认已经达到的目标或终止尚未执行的更新，不再次推进分支；不需要 GitHub 主密钥或联网。基线不一致时仍保持占用，不能绕过原操作发起新同步。

## 38. 持久任务推送预览与原生服务

迁移 027 将只读远端捕获/导出接入数据库请求和现有原生 Git 服务，依然不需要 Docker。先执行 `npm run db:migrate`，再正常重启已有的唯一 `npm run dev:git` 服务；完整本机启动器会自动加载新版。迁移 027 的四个处理器（工作区 Git、导入、同步、推送预览）共用两个通道；迁移 029 增加实际发送处理器，仍共用两个通道。更新后的 Web Git 状态查询依赖此迁移，不能只更新代码却遗漏迁移。

内部应用函数 `requestTaskPushPreview` 只接受源 revision、HEAD、run revision 和幂等键。任务当前 Developer 负责人或 Maintainer 按组织 MFA 规则申请/取消；范围、仓库、安装和目标引用由服务端派生。读取凭据前先去重，同键不同载荷拒绝；预览与暂存/提交、待处理快照互斥。完整原导出和 SQL hash 核验通过后才发布 ready，不授予远程推送权限。HTTP 与浏览器预览入口见第 39 节；实际发送入口见第 41 节。

读取期间每 500 毫秒检查当前授权，单次数据库检查有两秒独立本机超时。数据库失联后取消读取、独立清理令牌，旧请求只允许失败，不能重复下载或从后来源文件补建。同键请求用于查询已经提交的结果；显式新请求才分配新 ID。失败遗留目录暂不自动回收。此阶段不具备远端写入能力，不能把其释放占用规则用于未知 push。

专项入口为 `node_modules/.bin/tsx --test tests/collab/push-preview-broker.test.ts`，使用临时数据库、生成账户/App 密钥、真实本机 Pi 工具和回环 Git HTTP；另执行全量协作与隔离浏览器回归。协议见 [ADR-039](adr/0039-durable-task-push-previews.md)。完整历史浏览器确认及持久发送见后续第 39–41 节；PR/CI、真实外部账户以及可选 Docker 对等验收仍待完成。

## 39. 浏览器完整出站历史审阅

在已停止的任务运行下打开「任务推送预览」，点击「生成推送预览」。需要有效的 GitHub 仓库关联及独立 Git 服务；浏览器仅提交持久请求，不持有 Provider 凭据。页面刷新后仍可「重试同一预览请求」。同一工作区预览与暂存/提交、待处理快照互斥；排队/执行中的预览可以填写原因取消。

当记录显示「出站历史已固定」，点击「审阅全部出站历史」。这里列出所有新增提交及父关系，包含中间版本与合并支线；每个提交的文件变化相对此次核验的远端默认基线比较，页面明确显示目标任务 ref、旧/新 SHA、默认基线和固定清单 hash。提交每页 50 项，文件每页 100 项，可继续加载；未提交草稿不包括在导出中。

文本上限为 256 KiB / 8,000 行；二进制、UTF-16、长文本和超长提交说明有明确提示。文件在 2 MiB 以内、提交在既有 1 MiB 上限内时，可下载原始字节，并在浏览器复核 SHA-256 与长度。下载不会执行或渲染内容。旧基线的排除/疑似敏感内容不因下载而解禁；超过读取限制的旧文件不能视为已核对完整内容。换行、执行位、缺失侧和控制字符分别呈现。

本窗口的「已核对」标记绑定文件审阅 hash，但刷新或切换预览会清除，不是持久批准或推送授权；完整持久确认见第 40 节。项目访问撤销后，后续读取及下载都会拒绝；页面在授权刷新失败时清除已打开的历史。原导出缺失/损坏时拒绝读取，不从后来工作区补建。两个读取通道短暂繁忙时，页面只对无副作用的 GET 做有上限重试，并在卸载时取消旧读取。

接口包括 `runs/:id/push-previews`、`push-previews/:id` 及其 `cancel`、`history`、`download` 子路径。默认仍为原生版本，不需要 Docker；此阶段没有新迁移，已应用的 001–027 保持不变。完整协议见 [ADR-040](adr/0040-browser-outgoing-history.md)。

验证入口为 `tests/collab/task-push-history.test.ts`、`tests/collab/push-preview-broker.test.ts` 和完整隔离浏览器流程。调试本功能可用 `PI_COLLAB_E2E_FOCUS=push-history npm run test:collab:identity:e2e`，但它不替代不带该环境变量的全量浏览器验收。截图为 `test-results/collab/push-history-desktop.png` 和 `push-history-mobile.png`。受控远端发送与未知结果占用见第 41 节；PR/CI 仍须继续实现。

## 40. 持久确认完整历史与占用目标分支

需要迁移 028 与当前 Web 代码，执行 `npm run db:migrate` 更新已有数据库。本阶段没有新的 Git 服务处理器，不需要重复启动服务或安装 Docker。

打开固定出站历史，逐个打开提交说明及全部文件版本。每个文件需明确核对；二进制、超长文本、排除/遮蔽内容还需确认外部字节检查或无法读取范围。再确认该提交的说明、父关系和全部变更；没有文件变化的提交同样需要确认。加载并核对所有提交后，在「保存完整确认与目标占用」核对仓库、可见性、分支、旧/新 SHA 和完整历史披露范围，点击「保存确认并占用目标」。

记录保存成员、完整导出/远端观察 hash、每个提交的精确字节 hash 和路径计数，以及当前授权版本。此记录是成员对固定历史的声明，不证明软件能判断人是否理解了内容。后来的工作区改动不会加入原确认。本步骤只保存确认和分支占用，不发送代码；发送须按第 41 节单独请求。已有确认不会在软件升级后自动发送。

多成员或不同预览不能同时占用同一 GitHub 仓库 ID + ref。项目最多有 20 项未结算确认占用（永久隔离历史另行保留）；尚未进入发送队列的占用由当前任务负责人或维护者填写原因撤回。撤权、重新授权或任务/安装/绑定变化不会恢复旧确认，失效记录继续占用，直到获授权的人显式撤回。其他项目读者可查看，不具有操作权限。

响应丢失或页面刷新后，使用「重试同一推送确认操作」，它沿用原请求编号和内容。已撤回的原请求只返回旧记录，不重新占用。即使原导出后来损坏，已有确认历史和撤回入口仍可访问；新确认和实际发送必须重新核查原导出。

接口为 `push-previews/:id/confirmations`（GET/POST）和 `push-confirmations/:id/withdraw`（POST）。完整协议、未知远端效果的后续升级约束见 [ADR-041](adr/0041-durable-push-confirmations.md)。验收包含 `push-preview-broker.test.ts` 及完整隔离双浏览器流程；确认截图为 `test-results/collab/push-confirmation-desktop.png`、`push-confirmation-mobile.png`。这些本机证据不代表真实 GitHub 推送、PR/CI 或 Docker 对等验收。

## 41. 明确发送固定导出与未知任务封存

需要迁移 029、新版 Web 和唯一的 `npm run dev:git` 服务。先应用迁移，再正常停止并重启已有 Git 服务；五个处理器仍共用两个通道。不要另外启动重复服务。默认原生运行，不需要 Docker。旧确认不会因升级自动入队。

在完整确认记录下勾选「明确发送此已确认的固定导出」，点击「发送到已确认的任务分支」。只有当前任务 Developer 负责人或 Maintainer 可操作；原确认者与请求者的权限均须仍有效。浏览器先保存请求编号，再入队；关闭浏览器不取消任务。响应未知或刷新后使用「重试同一发送操作」。同一导出不接受第二个发送任务，换编号或换成员也不会重发。

发送前，Git 服务重新核验原导出与固定字节、成员权限、安装/仓库身份、可见性、保护规则、默认基线和任务旧提交。最终数据库授权事务得到成功确认后才发出一次 Git 请求。发送不修改原工作区、未提交草稿或公共基线，不授予 PR/合并资格。

状态分别为等待、处理中、远端确认接收、远端明确拒绝、确认未发送或结果未知；凭据清理另列。可填写原因「请求停止发送」，但授权记录之后无法保证撤销远端效果。发送任务接管确认后不能撤回确认释放目标。已知终态的后续操作须重新生成预览和完整确认。

结果未知会持续占用原 GitHub 仓库 ID + ref。看到旧 SHA、新 SHA 或令牌已撤销都不能证明原请求不会迟到生效。兼任项目 Maintainer、启用 MFA 的组织 Owner/Admin 可填写至少 20 字符原因、明确承认效果仍未知，再「封存未知任务并永久隔离旧目标」。该动作不释放旧分支；后续从新工作区和新生成任务分支继续。普通开发者及仅有项目维护权限的成员不能封存。

API 为 `push-confirmations/:id/send` 和 `push-deliveries/:id/actions`，均需身份与同源请求；状态随确认上下文返回。协议见 [ADR-042](adr/0042-durable-task-push-delivery.md)。专项仍在 `push-preview-broker.test.ts`，浏览器验收包含真实回环 Git 接收、取消、未知任务封存、两成员状态和刷新重试，截图为 `push-delivery-unknown-desktop.png`、`push-delivery-unknown-mobile.png`。本机生成凭据与回环接收不替代真实 GitHub 账户、模型调用、PR/CI 或 Docker 验收。

## 42. 草稿 PR 内部协议与只读准备

`lib/collab/git/github-task-pull.ts` 提供只读目标准备及一次草稿 PR 创建的 Provider 能力，后续第 43、44 节分别接入持久准备与显式创建。不要直接从 Web 调用；broker 必须先证明来源是已确认的持久推送结果、建立当前授权与全局 head 占用，再通过最终 SQL COMMIT 放行。

只读准备使用 `contents: read` / `pull_requests: read` 令牌，核对固定任务 SHA 并读取当前默认基线；默认分支前进不要求再次上传同一任务代码。创建阶段使用另一枚单仓库 `contents: read` / `pull_requests: write` 令牌，绑定生成的任务分支、目标版本、完整标题/正文和请求 hash。GitHub 不提供创建 PR 的双 SHA 原子条件，因此创建后的 `matching` 仅是带时间的版本观察，不是测试通过或合并资格；版本变化不会被自动修复或回滚。

PR 协议本身没有迁移或服务重启要求，001–029 保持不可变，默认仍不需要 Docker。专项：`node_modules/.bin/tsx --test tests/collab/github-task-pull.test.ts`。它先实际推送到本机 Git HTTP，再使用生成凭据及回环 REST 记录验证 PR 协议；不会创建真实 GitHub PR、发送外部通知或调用模型。设计、官方接口约束与持久化下一步见 [ADR-043](adr/0043-github-draft-pull-protocol.md)。

同轮修复了共享 Git 读取器与 `index-pack` 临时文件发布的竞争。部署此修复时应正常停止并重启已有 Git 服务，使长驻进程加载新版读取器；不要启动重复实例。读取器只对指定临时 pack 元数据的消失有限次重新执行完整检查，其他缺失、危险路径或目录替换仍拒绝。回归：`node_modules/.bin/tsx --test tests/collab/review-git.test.ts tests/collab/promotion-runtime.test.ts`，细节见 [ADR-021](adr/0021-immutable-integration-code-review.md)。

## 43. 持久的只读 PR 提案

需要迁移 030 与新版 Web。应用迁移后，正常停止并重启已有的唯一 `npm run dev:git` 实例；六个处理器仍共用两个通道，默认不需要 Docker。001–029 不修改。旧推送不会自动准备提案或创建 PR。

在「远端已确认接收」的发送记录中展开「准备草稿 PR 提案」，填写标题与说明后选择「读取目标并保存 PR 提案」。当前任务负责人 Developer 或 Maintainer 可以操作，组织 MFA 要求仍适用。其他项目读者可查看。待发送、未知或已封存的推送不能作为来源；安装/仓库关联变化后需要重新核验。提案只读取远端固定任务提交与最新目标基线，后续本机草稿不会混入，无须重推相同代码。

「已保存只读 PR 提案」可展开核对完整生成标题、正文和精确请求。源/目标 SHA、观察时间及原始请求/观察摘要均保留；当前本地权限有效并不保证远端分支未再次变化。发现已有 PR 只提供查看链接，不算本次创建成功。准备本身不创建 PR、不通知仓库成员；如需发送，进入第 44 节的独立确认流程。CI 尚未接入。

## 44. 明确创建草稿 PR

需要迁移 031。迁移后正常停止并替换唯一的原生 Git 服务，使七个处理器共用现有两个通道；不要额外启动一个重复实例。默认不需要 Docker。本机已应用 031 并核对摘要，001–031 均不可修改，后续 schema 修正须新增迁移。升级会保留旧 push 的普通占用和永久隔离，不能通过升级释放未知目标。

如果服务由 `npm run dev:local` 启动，Git 服务属于整组开发进程：任一子进程退出都会触发整组停止。先核对当前作业，再正常停止该启动器、执行 `npm run db:migrate`，最后重新执行 `npm run dev:local`；不要仅替换它的 Git 子进程。由单独 `dev:services` 持有的健康 PostgreSQL 可以复用，启动器会认证检查后连接，不需要重复启动数据库。只有原先单独运行 `dev:git` 时，才单独替换 Git 服务。

在已保存提案中展开「创建草稿 PR」，再次核对完整标题/正文、仓库、来源和目标版本，然后分别确认内容、GitHub 通知影响及版本可能变化，选择「确认发送并创建草稿 PR」。来源由服务器从原提案派生，不能在发送时替换分支、说明或摘要。原提案作者和当前发送者的任务/成员权限均须有效；组织 MFA 策略继续适用。

关闭浏览器不取消队列。响应丢失或刷新后，选择「重试同一 PR 创建操作」，沿用原编号；不能换编号重发同一提案。当前任务控制者可以填写原因请求停止。发送授权提交后，停止不能保证撤销已在途的创建请求。

「远端已确认创建草稿 PR」提供已核验的链接、创建回执和后续版本观察。创建成功、版本是否匹配及凭据清理分别显示；后续读取或令牌撤销失败不会抹掉已确认的创建。已有 PR 仅供查看，不接管。记录不是实时状态、CI 或合并许可；完整差异版本、持续跟踪、可信 CI 与受保护合并仍需实现。

结果未知时，同一稳定 GitHub 仓库 ID + 任务分支会同时阻止 push 和其他 PR 创建。当前没有 PR、正文标记或令牌失效均不能释放它。具备 MFA 的组织 Owner/Admin 兼项目 Maintainer 可填写至少 20 个字符的原因，明确封存并永久隔离旧分支；后续使用新工作区与新任务分支。这不关闭或修改任何远端 PR。

API 为 `pull-proposals/:id/create`（GET/POST）和 `pull-deliveries/:id/actions`（POST）。原生专项：

```bash

```

## 45. 读取已创建 PR 的状态与版本

需要迁移 032 与新版 Web/Git 服务；八个处理器仍共用两个通道。按第 44 节的启动器管理方式正常升级，不重复启动服务，也不需要 Docker。本机已应用 032 并核对全部 32 份摘要；001–032 均不可修改，后续修正须新增迁移。迁移不会自动读取已有 PR。

在已确认创建的 PR 下展开「远端 PR 状态与版本观察」。「刷新已有 PR 观察记录」只读取本地历史；「读取 GitHub PR 状态」才会提交后台只读请求。当前任务负责人 Developer 或 Maintainer 可发起，组织 MFA 策略仍适用；项目读者可查看保存记录。原创建者离开团队后，当前维护者仍可读取，不继承原创建权限。

新请求固定当前任务和观察版本，来源由服务器从已确认的 PR 身份派生。刷新或响应丢失后选择「重试同一 PR 读取操作」，不能修改原编号的内容。每个 PR 同时只有一项读取；排队/执行中可填写原因取消。失联的旧读取不会由另一执行者重放，终态后可以显式发起新读取。

观察是当时的 Provider 回应，不是实时状态；GitHub 返回的合并 SHA 也可能是临时测试合并。此功能不证明代码差异、CI、评审或受保护合并通过，不改变本机基线，也不能接管结果未知的创建。完整差异版本与固定版本 CI 已由后续章节接入；签名 webhook 与受保护合并仍待实现。

API 为 `pull-changes/:id/observations`（GET/POST）和 `pull-observations/:id/cancel`（POST）。原生专项：`node_modules/.bin/tsx --test --test-name-pattern='pull observation' tests/collab/push-preview-broker.test.ts`；浏览器专项沿用 `PI_COLLAB_E2E_FOCUS=push-history`，完整回归不设置它。截图为 `pull-observation-desktop.png`、`pull-observation-mobile.png`。详见 [ADR-046](adr/0046-durable-pull-observations.md)。


## PR 固定代码版本

在任务已创建的 PR 中打开“远端 PR 状态与版本观察”，先点“读取 GitHub PR 状态”。成功后展开“PR 固定代码版本”，点击“下载观察对应的固定代码”。后台作业完成后，可读取文件列表并查看逐行差异；同项目成员能读取相同版本，只有当前任务控制者能发起/取消下载。

此入口使用既有 GitHub App 与仓库关联，只申请单仓库 contents:read 权限，不会推送、评论或合并。没有真实安装时，用隔离测试验证完整路径：`PI_COLLAB_E2E_FOCUS=push-history npm run test:collab:identity:e2e`。测试运行在独立数据库/源码副本，GitHub REST 与 smart HTTP 都由回环服务提供。

失败或连接中断后查看原作业；界面出现“重试同一 PR 代码操作”时沿用原编号。旧成功版本保留，新的状态观察不会改变历史内容。标为“历史版本”的代码不能视为当前远端版本，CI/审批/受保护合并也仍需独立验证。实现边界见 [ADR-047](adr/0047-fixed-pull-revisions.md)。

## 固定 PR 版本 CI

迁移 034 增加持久 CI 规则与读取记录。应用迁移后正常替换原来唯一的 Git 服务，十个处理器共用两个通道；完整 `dev:local` 启动器会自动迁移。默认仍为原生运行，不需要 Docker。升级不会自动访问 GitHub。

在已下载的固定 PR 代码版本下展开「固定版本 CI 规则与结果」。项目维护者启用 MFA 后点击「编辑 CI 规则」，填写精确检查名称、生产者 GitHub App ID、观察有效期和变更原因。规则按仓库/目标分支共享，填写 App ID 前应确认该生产者的工作流和凭据配置可信。

任务控制者点击「读取此版本 GitHub CI」后，Git 服务才访问 GitHub；安装需要 contents、pull_requests 和 checks 读取权限。页面的「刷新已有 CI 记录」仅查询本地数据库。项目其他成员可查看同一版本的结果及规则。请求响应丢失时使用「重试同一 CI 操作」，仍用原编号。读取期间可填写原因取消。

检查须全部来自指定 App，且准确 head SHA 上每项恰有一个 completed/success 才通过。旧 SHA、同名其他 App、缺失、尚未完成、失败或重复均不通过。新读取一提交就使此前绿灯失效，新读取失败不会恢复旧绿灯；规则变化、来源变化和有效期结束也会失效。这一结果不等于远端评审或合并授权。

专项命令：`node_modules/.bin/tsx --test --test-name-pattern='pull checks' tests/collab/push-preview-broker.test.ts`。双浏览器回归沿用 `PI_COLLAB_E2E_FOCUS=push-history npm run test:collab:identity:e2e`；截图为 `test-results/collab/pull-checks-desktop.png` 和 `pull-checks-mobile.png`。协议与未完成范围见 [ADR-048](adr/0048-fixed-revision-ci.md)。

## GitHub 签名事件通知

迁移 035 让 `push`、`pull_request`、`check_run` 和 `check_suite` 通知及时使旧代码/CI 证据失效。默认依旧无 Docker，没有新后台进程；Web 只调用数据库内的专用验签函数，不读取验证密钥，也不获得 GitHub 私钥。需要先完成 GitHub App 安装登记及仓库关联。

1. 为 GitHub App 准备至少 32 字符的随机 Webhook secret，用无换行的 ASCII 文本保存在仅本人可读写的文件，例如 `.local/github-webhook.secret`。同一个 GitHub App 下的各安装使用同一 App secret。不要把它提交到仓库。
2. 在安装管理查看连接 UUID 和「配置版本」（未配置为 0），通过本机命令配置：

   ```bash
   npm run github:webhook -- --connection CONNECTION_UUID --actor OWNER_EMAIL --secret-file .local/github-webhook.secret --expected-version 0 --reason '启用此安装的签名 PR 和检查变更通知'
   ```

   操作者必须是该组织启用 MFA 的 Owner/Admin。命令返回版本及请求编号，不输出密钥；回应丢失时用相同参数加 `--request-id ORIGINAL_UUID` 重试。轮换使用当前版本和新密钥文件；停用加 `--disable`。每次配置使旧证据失效。
3. 在 GitHub App 设置中启用 Webhook，Secret 填相同字符串，URL 使用 `https://YOUR_HOST/api/collab/github-webhooks/APP_ID`，订阅上述四种事件。GitHub 无法直接访问 `127.0.0.1`；外网入口和 TLS 由部署者配置。本机调试可通过自己的受控转发入口访问，保持正确 Host；启动时 `PI_WEB_ALLOWED_HOSTS=YOUR_HOST npm run dev:local` 显式允许对应域名。程序不会替用户建立隧道或修改 GitHub 网站设置。
4. App ping 能通过验签，但不创建代码/CI 事件。实际通知在安装管理和 PR「远端变更通知」中显示；GitHub 出现失败投递时可重投。密钥轮换需同步 App 设置和所有已配置安装，旧密钥立即拒绝。

代码变更通知出现后，先重新读取 PR 状态，再下载固定代码版本和读取 CI。检查事件只要求重新读取 CI。重复通知不重复失效，旧 SHA 和无关分支不影响当前候选；延迟通知可能再次提示刷新，不能恢复旧审批或绿灯。通知不执行远端读取，不直接修改 GitHub 状态，也不是合并授权。

Webhook 验证密钥属于数据库私有数据，Web/Git 角色没有读权限；数据库备份包含该密钥，需要按数据库敏感备份处理。正常接口只显示配置版本、启用状态和通知时间，不显示密钥或原始 Webhook 正文。

专项命令：`node_modules/.bin/tsx --test --test-name-pattern='webhook' tests/collab/push-preview-broker.test.ts`；签名 HTTP 与双浏览器验收：`PI_COLLAB_E2E_FOCUS=push-history npm run test:collab:identity:e2e`。截图位于 `test-results/collab/pull-webhooks-*.png`，实现边界见 [ADR-049](adr/0049-signed-github-events.md)。
