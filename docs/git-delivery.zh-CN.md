# GitHub 固定版本评审与交付

F4 基础流程，2026-09-24。默认原生本机，Docker 不是使用前提。这里的团队评审、GitHub 原生评审和代码运行验收是不同证据，彼此不能替代。

## 成员操作

1. 使用已有任务分支推送、草稿 PR、状态观察和固定代码下载流程。打开任务「审阅全部出站历史」中的 PR 固定代码版本，在代码差异下方展开「团队评审与受保护交付」。
2. 维护者确认后可将草稿转为待评审。此操作会写入 GitHub 并可能触发仓库通知；不会自动合并。完成后重新读取 PR 状态和固定代码。
3. 另一位开发者、评审者或维护者查看固定 head/base 与代码差异，提交批准、修改要求或说明。任务负责人和 PR 创建发起人只能提供说明，不能算自己的独立批准。
4. 同一成员最新的批准/修改要求替代其旧结论，评论不撤销已有结论。有效修改要求阻止交付；至少一份有效独立批准才满足团队评审。成员离开、撤权再加入、任务归属变化或固定版本变化后，旧批准不能继续授权。
5. 发布并读取当前版本的 CI 规则与检查。维护者核对版本和交付说明，明确确认后提交合并。服务端在发送前再次核对任务、安装、仓库、评审及 CI；响应丢失的网页重试沿用原请求。
6. GitHub 确认合并后展示远端 merge commit。通过已有仓库「同步 GitHub 基线」获取该提交、执行快进检查并更新本地公共基线；不会把 API 返回的 SHA 直接冒充已同步的本地代码。

## 远端保护适配器的基础范围

当前支持 github.com、同仓库 PR、默认分支、普通 merge commit 与经典分支保护。App 需要 `pull_requests: write`；合并还需要 `contents: write` 和 `administration: read`。令牌只包含指定单个仓库，操作结束尝试撤销；私钥与短期令牌均不进入浏览器或 AI。

合并前必须读取并满足：受保护分支、管理员也受约束、严格要求最新基线的状态检查、至少一名原生评审、推送后旧批准失效、最后推送由其他人批准、没有 PR 绕过名单。平台团队批准不会伪造 GitHub 原生批准，GitHub 仍在合并请求时执行自身检查。

本版不适配 ruleset、merge queue、跨仓库 PR、squash/rebase merge。遇到这些情况不会绕过保护，可以在 GitHub 页面完成交付；后续适配仍保留在增强队列。原有推送目标保护保持不变。

## 结果与失败

交付状态持久化为排队、运行、待评审完成、合并完成、远端拒绝、未发送、未知或取消。排队请求可以取消；处理中的授权变化在发送前拒绝。已经开始但没有可靠响应的写入记为未知，同 PR 继续占用，不自动再次发送。

未知结果可通过现有「读取 GitHub PR 状态」查看真实状态，原请求仍保留未知标记。自动归因/解除未知占用以及更完整的运行中取消属于统一收尾；不能把没有回执解释为没有产生副作用。

## 安装、权限与凭据生命周期

组织管理页面保留安装状态、公钥指纹、版本及 webhook 状态，增加本机凭据是否存在和明确删除入口。删除会停用本机关联、递增授权版本、删除本机加密 App 私钥并停用 webhook 验证。代码、任务及审计保留；此操作不卸载 GitHub App，也不替代在 GitHub 删除旧 App 私钥。

本机管理员使用已存在的 CLI 刷新权限或轮换密钥；必须是组织管理员并启用 MFA，版本来自组织管理页。命令只读核验远端，不推送、不创建 PR。

```sh
npm run github:import -- refresh \
  --connection CONNECTION_UUID --expected-version VERSION \
  --actor ADMIN_EMAIL --reason '核对当前安装权限与仓库关联'

npm run github:import -- rotate-key \
  --connection CONNECTION_UUID --expected-version VERSION \
  --private-key /absolute/path/to/new-app-private-key.pem \
  --actor ADMIN_EMAIL --reason '轮换 GitHub App 签名私钥'
```

私钥文件须由当前用户拥有且权限为 0600。增加 `--enable` 可在成功重新核验安装和每个绑定仓库后启用原关联；未提供此选项时不会恢复已停用关联。删除凭据后需要 `rotate-key` 提供新密钥，单纯 `refresh` 无法恢复。每次成功刷新/轮换都递增安装及绑定版本，旧排队操作失效。可加 `--request-id UUID`，未知响应后复用相同输入查询原结果。

## 验证与剩余范围

本机协议验收使用真实回环 HTTP、生成的 App 密钥和真实 Git refs：草稿转待评审 → 重新固定版本 → 独立批准 → CI → 受保护合并 → 核对远端新提交。另验证保护不足不发送、权限/评审变化拒绝、未知写入不重复。安装生命周期覆盖权限刷新、私钥轮换、删除、幂等重试和重新接入。

真实外部 GitHub 账户、真实仓库保护配置及公网 webhook 的部署验收尚未执行；没有向用户仓库发起外部写入。功能骨架之后继续 F5 资源与费用配额，保留真实部署验收与上述适配扩展。

验收证据：交付专项 3 项、安装/PR 回归 23 项及双成员网页专项通过，类型检查与 lint 通过。网页实际经过草稿转换、独立批准、CI、合并和结果同步；桌面/390px 截图位于 test-results/collab/pull-release-*.png。主实例升级 040。
