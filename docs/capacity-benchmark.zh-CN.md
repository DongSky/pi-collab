# 原生与 Docker 并发基准

本基准验证原计划 §11 的本机并发主线：两个隔离组织、20 名已登录成员、8 个真实 Pi 进程、每个运行 3 个事件订阅者、100 次并发重复启动，以及满额排队和断线游标回放。使用生产 Next 产物和真实常驻执行器，本机模型协议服务驱动 Pi 调用 Bash 与协作工具；不调用付费模型。

## 执行

先按 [安装包流程](release-packaging.zh-CN.md) 在独立目录生成并安装生产产物。开发 checkout 不运行构建。

```bash
npm run test:collab:capacity -- \
  --web-root /absolute/installed-release \
  --runtime native --duration-seconds 60 \
  --output test-results/collab/capacity-native.json
```

`--runtime` 支持 `native` 和 `docker`，默认原生；`--duration-seconds` 支持 10–900 秒，默认 30 秒；长测每 10 秒规划一轮 Pi 协作说明，并每 30 秒输出负载进度。Docker 使用已安装的 runner 镜像，实际核验挂载与 8 个运行中容器，报告记录镜像和 Docker VM 的 CPU／内存。

脚本会校验安装包，并要求其 app/lib/components/hooks 和执行器入口与当前源码字节一致，拒绝拿旧生产代码冒充当前实现。它创建独立测试数据库、临时工作区和私有服务日志，启动独占的临时 PostgreSQL 集群，避免与开发服务及全量测试竞争数据库连接；不更改开发账户、项目或模型凭据。测试成功后关闭进程并删除测试数据库、工作区；失败保留私有日志，不能将日志原文作为公开报告。

认证会话由本机测试身份 API 生成，随后通过 HTTP 请求验证身份；这不是登录突发流量或浏览器渲染性能测试。20 个客户端在指定持续时间内交替请求项目列表／详情，每次响应后间隔 150 ms，同时保持 24 个 SSE 读取者。模型协议按采样时长分散产生协调说明，让事件覆盖整个测量阶段。100 次相同幂等键的启动请求必须只有一个 run 和一条启动命令。8 个不同原生 PID 或 Docker 容器进程的活性、运行归属和工作区同名文件内容都要实际核对；第 9 个任务必须排队。Pi 通过自己的协作工具发送持久说明，不能由测试直接伪造运行事件。

普通 API 的样本包含发送、响应读取及 JSON 解析；P95 使用排序后的上取整分位数。协调事件延迟为数据库事件记录时间到客户端收到完整 SSE 帧的差，包含提交及服务端轮询时间。断线测试从最后事件游标重连，并检查断线期间新写入的持久说明被补齐；并不代表任意规模完整历史都已通过 5 秒恢复验收。

## 已记录结果

[原始 JSON](evidence/capacity-native-2026-09-24.json) 为本机 macOS arm64、Apple M4 Pro、12 逻辑核、48 GiB、Node 26 的短时结果，生产包版本 `32f0974`。控制层、执行器、数据库及其他开发服务共享宿主机，未施加参考环境的 4 vCPU/8 GiB 和 8 vCPU/32 GiB 限制。

- 20 个认证客户端，两个组织，8 个不同的活动 Pi PID，24 条 SSE 订阅。
- 1,000 次项目 API 请求，采样约 8.28 秒；API P95 **30.45 ms**，最大 **42.37 ms**。
- 243 个协调事件接收样本，P95 **984 ms**，最大 **1,003 ms**。P95 满足目标，但接近 1 秒边界，不能宣传所有事件均小于 1 秒。
- 断线期间的持久说明约 **57.65 ms** 补齐。
- 8 个运行共同活动约 **8.4 秒**；100 次重复启动、满额排队、工作区内容隔离与跨组织订阅拒绝均通过。

本轮还修复启动器配置遗漏：`PI_COLLAB_EXECUTOR_CAPACITY` 原先在 `dev:local`／团队监督进程创建执行器环境时被丢弃，导致自定义节点容量失效。现在显式传递，默认仍是 8，由执行器校验 1–32；不会把其它宿主配置一并传入 AI。部署环境专项覆盖了配置传递和秘密隔离。

## 60 秒持续负载

同一脚本已接入两个后端，每轮持续产生 API 请求与 Pi 协作说明，并核验 8 个活动原生进程或容器。两轮均有 20 个认证客户端、两个组织、24 条订阅和 6,960 次普通项目 API 请求；重复启动、满额排队、文件隔离与跨组织订阅拒绝继续通过。

- [原生完整结果](evidence/capacity-native-60s-2026-09-24.json)：共同活动约 60.26 秒；API P95 31.32 ms；243 个事件接收样本 P95 967 ms、最大 1,037 ms；游标回放约 56.77 ms。
- [Docker 完整结果](evidence/capacity-docker-60s-2026-09-24.json)：共同活动约 60.15 秒；API P95 30.76 ms；241 个事件接收样本 P95 865 ms、最大 869 ms；游标回放约 56.68 ms。真实运行的 8 个容器位于 12 vCPU、约 7.65 GiB 的本机 Docker VM，镜像摘要在 JSON 中。

两轮 P95 都满足本机采样门槛；原生的个别事件仍超过 1 秒。工作负载是轻量文件写入与平台协调，不代表 8 个大型编译、真实模型长任务或参考硬件性能。新参数默认 30 秒，可显式运行 10–900 秒；60 秒只是持续工作主线验证，不是长时间浸泡测试。

## 尚未覆盖

这次是短时并发基准，不是长期稳定性、全 API 性能、浏览器输入到渲染延迟、模型质量或外部 Provider 延迟验收。指定 CPU／内存参考拓扑、长时间浸泡、大仓库／长历史、RPO/RTO 及真实团队试点仍需各自测试。10 个独立 Yjs 客户端的重排／重放收敛，以及浏览器关闭后的未同步草稿恢复另见 [共编说明](collaborative-editor.zh-CN.md)。报告保留这些限制，不能仅凭本结果宣布完整 Beta 达标。

## 10 分钟持续负载（2026-09-25）

初次延长测试与全量回归共用了开发 PostgreSQL 集群（不同数据库名），触发默认 60 连接上限。测试中的模型请求失败释放名额，使第九个运行进入执行；全量回归同时记录 PostgreSQL `53300`。该轮失败不能算作容量通过。基准已改为随机端口的独占临时 PostgreSQL 集群，保持默认连接上限；失败会保存私有运行状态摘要，便于定位。

修正后 [原生完整结果](evidence/capacity-native-600s-2026-09-25.json)：20 个认证客户端、两个组织、8 个真实 Pi 进程共同运行约 600.18 秒，24 条 SSE 订阅；74,101 次 API 请求，P95 31.89 ms；1,441 个事件样本，P95 954 ms、最大 1,028 ms；断线回放 59.17 ms。100 次重复启动唯一化、满额排队、独立文件和跨组织拒绝全部通过。每个 Pi 实际发送 60 轮协作说明。

生产代码为 `13e0a8b`，测试与文档为 `4ccd9d6`，运行代码字节已比对。10 分钟验证不代替数天浸泡、参考硬件和团队试点。

同轮 [Docker 完整结果](evidence/capacity-docker-600s-2026-09-25.json) 也通过全部门槛：8 个真实容器共同活动 600.25 秒，20 个认证客户端、24 条 SSE；72,715 次 API 请求，P95 41.43 ms；1,441 个事件样本，P95 952 ms、最大 1,020 ms；回放 73.91 ms。容器执行的生产包仍为 `13e0a8b`；报告的 `sourceCommit` 在结束时取值为 `3e00e11`，不能据此声称该新提交已包含在运行包中。
