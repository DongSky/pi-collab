# GitLab 协作交付

GitLab adapter 在迁移 052 中接入项目。默认原生运行，无须 Docker。导入、准备、推送、MR 操作由单独 Git broker 执行，Web 和 AI 不读取 GitLab 令牌。

## 接入与权限

部署管理员准备只允许当前 OS 用户读取的令牌文件，使用 GitLab **项目访问令牌**（项目 Maintainer，`api` 和 `write_repository`）。注册时实际核对机器人身份、令牌归属和状态、数字项目 ID、仓库 URL、默认分支及访问级别。普通个人令牌不接受。组织管理员同时需要项目维护者角色及本地 MFA。

```bash
npm run gitlab:connect -- --project PROJECT_UUID --actor admin@example.com \
  --origin https://gitlab.example.com --remote-id 123 --name team-repo \
  --token-file /private/path/gitlab-token --reason '连接团队已授权的 GitLab 项目'
```

支持 HTTPS 根来源及本机协议验收的字面回环地址；不支持安装在 URL 子路径的 GitLab。令牌经现有 Git 主密钥加密，绑定连接及项目 ID。本机配置文件不作为网页输入。

轮换时在相同命令上追加 `--connection CONNECTION_UUID --version CURRENT_VERSION`，并指定新令牌文件。连接 ID 与导入历史保持，连接版本递增，旧排队操作失效；不会自动重新启用停用的连接。旧令牌在 GitLab 的实际吊销仍由管理员完成。当前连接版本由项目 GitLab API 的 `connections[].version` 返回。

## 使用流程

1. 在任务页的 GitLab 协作交付区域填写操作说明，维护者点击“导入 GitLab 仓库”。导入实际 Git 对象与默认分支完整历史。
2. 任务在独立工作区完成，创建快照、通过固定验证并发布成果。
3. 负责人或维护者选择该成果，准备固定变更预览。检查完整修改前后文本和排除项，然后勾选确认并发送。
4. 服务向独立任务分支发送一次精确 Git 更新；收到确认后创建草稿 MR。MR 使用**成果快照提交**，不复制 AI 中间提交历史。排除文件保留远端原值。首版限 100 个变更文本文件及 2 MiB 修改前后字节，二进制和疑似秘密拒绝发送。
5. 独立维护者/评审者查看同一不可变计划，批准或拒绝。作者及任务负责人不能自批。批准绑定完整计划 hash。
6. 有 MFA 的维护者将草稿转为待评审，明确请求合并。服务重新检查本地批准、拒绝记录、当前权限、成果有效性、MR 头提交、GitLab 可合并状态及该提交的成功 pipeline。
7. 合并后点击“同步 GitLab 默认分支”。新对象经独立暂存目录核验后同步，后续任务可以使用新基线；旧工作区和旧快照保持不变。

观察 MR 仅从 GitLab 读取，不执行合并，历史状态保留为独立操作记录。成员退出、权限版本变化、连接停用/轮换会阻止待执行写入。所有请求有持久幂等键、当前授权检查及审计。相同连接的 broker 工作串行执行。

## 失败边界

页面展示排队、运行、完成、失败和结果待核查。网络请求结果不明时可按原请求键重查；Git 发送、创建 MR 或合并的结果不明不会自动重发。未知投递保留占用，需要核对远端后人工处理，不宣称已有所有未知写入的自动恢复。中断的只读导入可以重新导入到新目录，旧操作仍保留在历史中。同步可重新请求，不覆盖旧任务文件。

## 已验证与后续范围

3 项数据库/实际 Git 专项涵盖导入、受限凭据、真实 Pi 无推理成果、固定预览、丢失推送回复不重发、独立评审、CI 门禁、真实 Git 合并、新基线任务、轮换和停用。双成员网页完整主流程、权限/CSRF及桌面/390px 页面已通过。

验收使用本机 GitLab REST 协议服务与真实 Git 仓库；pipeline 状态是协议夹具。未向外部 GitLab 账户写入，未宣称真实 GitLab CI、公网部署、GitLab webhook、merge train、squash/rebase 或大文件/LFS 交付已经验收。外部集成验收及复杂写入恢复继续保留在收尾范围。
