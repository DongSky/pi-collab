# 接口兼容检查基础

任务页「接口契约与确认」现在为每个提案显示与**它引用的固定父版本**的结构比较。生产者和受影响任务负责人读取同一份报告；报告显示具体 JSON 路径、规则版本、父定义 hash 和提案定义 hash。提案或父版本本来已不可变，报告由这些持久来源确定性计算，不另设可被用户伪造的“检查通过”记录。

JSON Schema 首版识别新增必填字段、类型收窄/改变、允许值减少、数值/长度/数量约束变严、禁止额外字段以及闭合对象字段删除，并检查嵌套属性和数组项。它比较的是可接受数据的约束变化，不把该结果当作响应类型、实现代码或消费者程序的兼容性证明。

OpenAPI 3 首版识别方法/路径删除，并将其他操作或全局定义变化列为待核对。引用、组合 Schema、认证和请求/响应类型变型等完整语义未实现；文本契约也明确标记需要人工核对。未经覆盖的语义、无效声明或截断报告不能显示为“兼容”。

如果用户把提案标为“兼容扩展”，检测却发现风险，页面单独显示矛盾提示。受影响任务负责人使用现有确认/拒绝入口处理，维护者裁决、审计、版本失效及 Git 评审继续生效。自动检查不会替任何成员批准提案，也不会调用模型、启动代码或修改源码。

## 实现与基础边界

- API：现有 `GET /api/collab/tasks/[id]/contracts` 增加每项提案的 `compatibilityReport`，继续使用项目成员权限与 RLS；客户端不能指定任意仓库路径或父定义来冒充已存储报告。
- 数据：复用不可变的 `contract_proposals` 与 `contract_revisions`。无需数据库迁移，当前主实例仍为 051。
- 规则：`contract-structure-v1`，最多展示 100 条发现、最多 24 层递归；超限显式提示。报告状态是首次版本、发现风险、存在未覆盖语义或已覆盖规则未发现收窄，均不是兼容认证。
- 未实现：源代码 AST/调用图、完整 JSON Schema 子类型求解、引用解析、自动生成契约测试、运行中的 mock 服务。这些属于后续增强，不冒充首版功能。

## 验收

- `node_modules/.bin/tsx --test tests/collab/contract-compatibility.test.ts`：字段/类型/边界、递归、未覆盖语义、稳定依据、OpenAPI 删除。
- `node_modules/.bin/tsx --test tests/collab/contracts.test.ts`：既有契约确认、固定运行输入、权限和版本规则回归。
- `PI_COLLAB_E2E_FOCUS=compatibility npm run test:collab:identity:e2e`：真实持久父版本、网页提交、两个任务负责人看到同一风险、人工标签矛盾、消费者拒绝、匿名拒绝、桌面/390px 页面。
