# 运行中 AI 的基线与输入更新

原计划 8.5 要求基线更新在安全点传达给正在工作的 AI。原有 `collab_get_context` 已返回工作区基线、仓库当前基线和固定输入的有效性，但依赖模型主动读取。现在受管理的 Pi 扩展在每次模型请求前自动读取一次该状态；完成工具批次后再读取，不打断正在执行的工具。

注入内容只包含平台计算的 `workspaceSha`、`currentSha`、`changed` 和 `inputsCurrent`，以及固定的处理说明。评论、其他 AI 的说明、契约正文和项目记忆不会被自动带入；讨论选入模型上下文仍走当前控制者明确确认的流程。

基线不同或输入失效时，AI 获知后续成果需要针对当前目标重新整合与验证。平台不因此 rebase、修改 checkout、替换固定输入、启动新的模型轮次或授予合并权限。真正的发布和合并继续由服务端版本门禁约束，不能只相信模型是否遵循提醒。

每次观察沿用运行专属的协调能力，服务端重新检查租约和权限，并保留并发与频率限制；单次读取最多等待 2 秒，无后台轮询或自动重试。读取失败、限流、撤权或返回格式错误时发送“当前有效性未知”，不重用之前的有效状态。模型网关仍独立验证运行授权。

观察仅进入本次模型请求，不追加到持久会话、不累积历史提醒，也不作为用户指令记录。已有基线事件、收件箱和项目页面仍是成员查看基线变化的入口。空闲 AI 不被唤醒；下一次正常模型请求才会读取。恢复/新启动的 Pi 会自动加载新扩展，已有进程不会热替换扩展。

## 验证

- 原生与 Docker 各运行真实 Pi，使用本机模型协议服务：第一轮请求期间改变仓库基线，下一轮模型输入立即包含新 SHA；模型没有调用协调工具，checkout HEAD 与写入文件保持原样，总模型请求数仍为 2。
- 扩展专项确认输入失效、只选择平台字段、不会把评论或能力令牌带入模型、失败后不重用旧状态。
- 23 项协调与本地 Git 推进回归通过，包含双 Pi 协调、真实基线推进及旧工作区固定输入检查；类型检查和 lint 通过。

无数据库迁移，无外部模型推理或 Git 写入。默认原生，Docker 使用同一扩展源码构建。
