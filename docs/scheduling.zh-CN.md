# 项目优先级、公平调度与等待保护

原计划 8.2 的并发、依赖和子 AI 限制已有基础；迁移 066 补齐项目优先级及防止新任务持续插队的等待保护。项目“资源与费用”页面新增“调度与等待队列”，成员可查看当前项目的排队任务、等待分钟数、等待保护、依赖和配额提示。维护者启用 MFA 后可修改项目优先级，并填写审计说明。

## 确定的领取顺序

执行器仍先筛选符合运行方式、授权、依赖、成员/项目配额、子任务配额和工作区额度的候选。仅在这些候选中按以下顺序领取：

1. 等待满 30 分钟的任务先领取，彼此按提交时间和运行 ID 排序。
2. 其余任务优先分配给活动运行较少的成员，沿用已有公平分配规则。
3. 成员占用相同时比较项目优先级和等待时间。低/普通/高分别提供 0/5/10 分钟的等效等待优势；等待足够久的低优先级任务仍可排在新高优先级任务之前。
4. 仍相同则按提交时间和运行 ID 排序，结果确定。

默认项目优先级为普通。调高优先级不抢占活动任务、不提高并发额度、不抢占共享资源，也不能让未满足依赖的任务启动。30 分钟是排序保护阈值，不是启动时限；额度不足、没有兼容的执行器或上游未交付时继续等待。不同运行方式仍只由支持它的执行器领取。

页面只展示当前项目最多 100 个排队任务的参考顺序及总数，不披露其他项目内容，也不把跨项目参考顺序承诺为实际下一个执行任务。页面约每 5 秒更新；配置编辑期间保留表单。修改优先级影响下一次领取，不改变已有运行的工作区、模型、固定输入或租约。

## 数据与接口

- `collab.project_scheduling` 保存项目优先级和乐观版本；写入只经过受限函数，维护者/MFA/当前成员权限在数据库内重查。
- 配置使用 `expectedVersion` 和幂等请求编号；同编号同内容返回原结果，修改内容或过期版本拒绝。审计事件为 `scheduling.configured`。
- `GET/PUT /api/collab/projects/[id]/scheduling` 提供共享读取与维护者设置，写入沿用同源与登录校验。
- 原子调度继续使用原领取函数的锁顺序、租约、依赖固定和配额门禁；新规则仅替换排序。原生和 Docker 共用该数据库调度，未增加调度器副本。

## 验证范围

4 项真实数据库专项验证跨项目优先级、等待时间抵消优先级、公平份额、等待保护、严格依赖、成员额度，以及配置权限/MFA/幂等/审计。17 项执行与子任务回归验证原领取和父子 AI 主流程仍可用。双成员网页验证配置、刷新持久性、成员只读、同源保护及包含等待保护的队列展示；桌面与 390px 页面截图保存在 `test-results/collab/scheduling-*.png`。

这仍是单实例的确定性领取策略。多节点容量公平、可配置组织级权重、执行成本预测和抢占式调度不包含在此次基础实现中。
